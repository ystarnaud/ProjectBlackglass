# Architecture Decisions

Short record of decisions that are likely to matter later. Newest last.

## 001 — Engine version: Unity 6.3 LTS (6000.3.25f1)

- **Decided:** Create the project with Unity 6.3 LTS, 6000.3.25f1 (installed via Unity Hub, 2026-10-03).
- **Why:** Current LTS stream, supported until December 2027. Input System and URP development is focused on Unity 6.
- **Rejected:** 2022.3.46f1 (already installed, but its free LTS support has ended; we would have to upgrade soon). Unity 6.0 LTS (support ends October 2026). 6000.6 (newer, but not an LTS release).
- **Implications:** Everyone working on the project needs exactly this Editor version (see `ProjectSettings/ProjectVersion.txt`). Upgrade only deliberately, as its own change.
- **Known issue:** Unity 6 requires Windows 10 21H1 (build 19043) or newer. The current development machine runs Windows 10 2004 (build 19041). The Editor works but prints an "unsupported OS" warning at every launch. Built Windows players ran here without any warning. Updating to Windows 10 22H2 meets the minimum. Windows 10 itself has been out of mainstream support since October 2025, so Windows 11 is the longer-term option.

## 002 — Render pipeline: URP

- **Decided:** Universal Render Pipeline, set up from Unity's "Universal 3D" project template.
- **Why:** Unity's default for new 3D projects. The Built-in pipeline is being deprecated, so starting there would mean migrating materials and lighting later.
- **Rejected:** Built-in (deprecated); HDRP (heavier and aimed at high-end visuals we don't need).
- **Implications:** Use URP shaders (`Universal Render Pipeline/Lit`) for placeholder materials. Pipeline assets live in `Assets/Settings/`, where the template put them.

## 003 — Repository and folder layout

- **Decided:** The Unity project sits at the repository root. All of our own assets go under `Assets/_Project/`. Folders are created only when something goes in them.
- **Why:** The root layout is the Unity convention and matches the standard Unity `.gitignore`. One project folder keeps our content separate from Unity-generated and third-party folders (`Settings/`, `Plugins/`, imported packages). Empty folders cause churn: Git doesn't track them, and Unity deletes their orphaned `.meta` files.
- **Rejected:** A `UnityProject/` subfolder (only useful if the repo will hold non-Unity code). A large pre-made folder tree (speculative).
- **Implications:** New top-level categories (for example `Scripts/`, `Prefabs/`, `Materials/`) are added under `Assets/_Project/` when the first real asset needs them. `Prefabs/` was added on 2026-10-04 for the first prefab (`FriendlyUnit`).

## 004 — Line endings

- **Decided:** `* text=auto` for everything. On top of that, the formats Unity writes as text (`.unity`, `.prefab`, `.asset`, `.meta`, `.inputactions`, `.asmdef`, `.json`, …) get `eol=lf`, so they stay LF in the working tree too. Those rules set only `eol` and never force `text`.
- **Why:** This machine's Git has `core.autocrlf=true`, and Unity writes LF. Without the rules, these files check out as CRLF, and once Unity re-saves them they show as modified even though nothing changed. `text` is not forced because some `.asset` files are always binary (LightingData, NavMesh, TerrainData). Forcing `text` would make Git rewrite CRLF bytes inside them and corrupt them on commit. That was reproduced in a test repo.
- **Implications:** C# scripts and other hand-edited files follow each machine's `autocrlf` setting (CRLF on Windows). When a new Unity text format appears, add an `eol=lf` line for it. Git LFS is not used yet. Add it deliberately when large binary art arrives.

## 005 — Package baseline

- **Decided:** Keep the URP template's packages that serve the prototype: URP, Input System, Test Framework, uGUI, and the Rider/Visual Studio integrations. Remove the template extras: Timeline, Visual Scripting, Unity Version Control (`collab-proxy`), Multiplayer Center. Built-in engine modules stay at Unity's defaults. Versions match what Unity 6.3 recommends.
- **Why:** `CLAUDE.md` asks for no unnecessary packages. Each removed package can be added back with one line in `Packages/manifest.json`. Pruning built-in modules would save little and cause confusing missing-type errors later.
- **Implications:** `com.unity.ai.navigation` 2.0.14 was re-added on 2026-10-04 for prototype unit movement (NavMeshAgent + a baked NavMeshSurface). `Packages/manifest.json` also lists `com.unity.inputsystem` under `testables`, which is test-only and exposes `InputTestFixture`. Test runs must therefore filter to our assemblies (`Tools/run-tests.sh` does this).
- **Input:** The project uses the Input System package only. The legacy Input Manager is disabled (Player Settings → Active Input Handling). The project-wide actions asset is `Assets/_Project/Input/BlackglassControls.inputactions`, which replaced Unity's template asset and kept its GUID (see 008).

## 006 — Unit commands are data; units execute them

- **Decided:** Gameplay orders are small immutable objects (`MoveCommand`, `AttackCommand`, `StopCommand`, base `UnitCommand`) passed to `CommandableUnit.Issue(command, mode)`. The unit and its components (`UnitMover`, `UnitAttacker`) decide how to carry them out.
- **Queue (Phase 2, 2026-10-04):** each unit keeps a `CommandQueue`: the current order plus pending ones.
  - `IssueMode.Replace` (the default) drops all orders and starts the new one now. `IssueMode.Append` runs it after the pending ones, or now if the unit is idle.
  - `StopCommand` halts the unit and clears every order, whatever the mode.
  - `Issue` checks first and returns false without changing anything when an order can't be carried out: no walkable point within 2 m of a move destination, or a dead or inactive attack target.
  - When the current order finishes, the next pending one starts in the same frame. A pending order that can no longer start (its target already died) is skipped.
  - Tactical pause needs no special handling: orders issued while paused are queued normally and run once simulation time moves.
- **Groups:** `GroupOrders.Issue(units, command, mode)` gives one order to several units. Moves are spread over a hexagonal lattice 1.5 m apart (`GroupMoveOffsets`); a slot off the NavMesh falls back to the clicked point.
- **Direct control (Phase 3, 2026-10-04):** `CommandableUnit` also takes a held **move intent** (`SetMoveIntent(direction)`), which is not a command. While it is non-zero and simulation time runs, the unit clears all of its orders (current and pending, as Stop does) and steers with `UnitMover.Steer`. Orders and direct control share `UnitMover` and `UnitAttacker`; nothing else drives them. An order issued while the intent is held is accepted, then dropped on the next simulation frame (keys win while held), except an ability, which still runs (see 025).
- **Cover (Phase 6, 2026-10-05):** a fourth command type, `MoveToCoverCommand(CoverPoint)`, with its cases in `CommandableUnit` (019); `Issue` also refuses a point another unit holds.
- **Why:** Player input, groups, AI and scripts all produce the same objects without knowing movement or combat rules. Commands stay testable and loggable. Keeping the queue inside `CommandableUnit` keeps one entry point for orders.
- **Rejected:** Classic `Execute(unit)` / `Begin/Tick/Cancel` commands, which would put long-running chase/attack logic into command classes. Direct methods on the unit (`MoveTo`, `Attack`), which leave no command value to queue or send from AI. A separate queue component feeding `Issue`, which would mean two entry points coordinating by polling.
- **Implications:** Interact will be a new `UnitCommand` subclass with cases in `CommandableUnit`. Weapon choice (a later phase) would be data on `AttackCommand`. There is no change event; debug views read `CurrentCommand`/`PendingCommands` each frame.
- **Amended (Phase 7, 2026-10-06):** an `AbilityCommand` joins Move, Attack, MoveToCover and Stop; it is validated at issue and again when it runs (decision 025).

## 007 — Tactical pause owns time scale

- **Decided:** `TacticalPause` is the only code that writes `Time.timeScale` (0 when paused, the previous value on resume). Simulation code (unit orders, NavMesh movement, attack cooldowns, hit flash) uses scaled time and stops. Camera, input and debug UI use unscaled time or input callbacks and keep working. Unit orders don't advance while simulation time is frozen, but commands are accepted while paused.
- **Why:** A single owner keeps pause behaviour predictable and lets it evolve, for example into slow motion or per-system clocks, without hunting down scattered `timeScale` calls.
- **Implications:** Any new system must choose scaled or unscaled time deliberately. Systems reference `TacticalPause` through the Inspector; it's not a singleton.
- **Pause frame (Phase 3, 2026-10-04; closed in Phase 4):** `Time.deltaTime` still holds the previous frame's value on the frame `Pause()` is called, so a scaled-time check alone lets one more frame of simulation through. Since Phase 4 every simulation `Update` (`CommandableUnit`, `UnitMover.Steer`, `EnemyAI`, `HitFlash`, `AttackLineView`) checks `SimulationTime.IsRunning` (scaled delta time **and** time scale above zero), so no order, hit or AI step runs on the pause frame (see 013).

## 008 — Input mapping and click vs drag

- **Decided:** Project-wide actions live in `Assets/_Project/Input/BlackglassControls.inputactions`, with three maps:
  - **Camera:** Pan (WASD), Rotate (Q/E), RotateDrag (right button), PointerPosition, Zoom (wheel).
  - **Commands:** Command (left button), PointerPosition, TogglePause (Space), Modifier (Shift), Stop (X), ClearSelection (Esc).
  - **Character** (Phase 3, 2026-10-04): Move (WASD), Takeover (V), CycleCharacter (Tab), CycleReverse (Shift; held with Tab it cycles backward, see 012) and ToggleFollow (F, 2026-10-05, see 022).
- **WASD is shared** by `Camera/Pan` and `Character/Move`. The mode decides which one acts: while the active character is being driven (takeover on, not paused) the camera ignores Pan, and otherwise `DirectControlInput` ignores Move. **Shift is shared** by `Commands/Modifier` and `Character/CycleReverse`: each map owns its own action so no component enables or disables another's.
- **Left button** (Phase 2, 2026-10-04): a quick click (≤ 6 px of movement) acts on what is under the cursor:
  - a friendly unit (`SelectableUnit`) is selected; with Shift it is added or removed;
  - anything else is an order: Attack on a living `Health`, otherwise MoveToCover when a cover point lies within 1 m of the click (Phase 6, 021), otherwise Move. Shift queues it instead of replacing. **The order goes to the selected units whenever any are selected or the game is paused; with nothing selected in real time it goes to the active character** (Phase 3 sent every real-time click to the active character; changed 2026-10-04 after Phase 4 because the owner wants real-time squad orders back, see 011).
  - A left-drag box-selects the roster units inside the box (Shift adds; an empty box clears).
- **Right button** is camera-only: right-drag rotates (horizontal) and tilts (vertical, 25°–85°). `ClickDragDetector` holds the click-versus-drag rule for both buttons.
- **Why:** The owner chose left-click commands (2026-10-04), then chose to keep them when selection arrived: one button for "act on what I click", the other for the camera. This is also the convention of party-based tactical-pause games.
- **Consequences:** Clicking the ground is Move, so it can't clear the selection; Esc does. Clicking a friendly always selects it, so a move can't be ordered onto a spot where a friendly stands.
- **Implications:** Input components only create commands, change the selection, call `TacticalPause`, set the active character's move intent through `CommandableUnit.SetMoveIntent`, toggle `ActiveCharacter` takeover or follow (022), or ask `ActiveCharacter` to cycle. They never touch `UnitMover`, `UnitAttacker`, the NavMeshAgent or `Health`. Rebinding means editing the actions asset. The keys 1–9 are still free; they may be wanted for both weapon choice and control groups later.
- **Amended 2026-10-05 (Phase 6.5, see 024):** actions were renamed by name only (`Takeover` → `ToggleCharacterControl`, `CycleCharacter` → `NextCharacter`, `TogglePause` → `ToggleTacticalPause`, `Modifier` → `QueueModifier`, `ClearSelection` → `Cancel`), every binding now belongs to a binding group (keyboard/mouse bindings are in `KeyboardMouse` and are unchanged), and gamepad bindings, the `UI` map and new tactical actions were added. The keyboard/mouse behaviour described above is unchanged.

## 009 — Code assemblies and tests

- **Decided:** Runtime code lives in the `Blackglass` assembly (`Assets/_Project/Scripts`). Tests are in `Blackglass.Tests.EditMode` (pure logic) and `Blackglass.Tests.PlayMode` (runtime behaviour, plus simulated input via `InputTestFixture`). Components expose `internal Initialize(...)` for test wiring. Scenes wire them through serialized fields. Tests run in batch mode via `Tools/run-tests.sh`, with the Unity Editor closed.
- **Why:** Separate assemblies keep compile times short and dependencies explicit. Automated tests cover the control loop so later changes can't silently break it.
- **Implications:** New gameplay code gets EditMode tests for pure rules and PlayMode tests for runtime behaviour.
- **Gotcha:** PlayMode tests that load a scene containing input components must derive from `InputTestFixture`, load the scene inside the test (not in `[UnitySetUp]`), and destroy the scene's objects before `base.TearDown()`. Otherwise their input-action state leaks into later fixtures (see `PrototypeSceneTests`).

## 010 — Unit selection

- **Decided:** `UnitSelection` (a component on `Systems`, wired through the Inspector) holds the selected units and the **roster** of units the player controls. `SelectableUnit` marks a unit the player may select and carries its `IsSelected` state; `SelectionIndicator` shows a ring. Selection holds state only: `PlayerCommandInput` decides what to select, and while paused, orders go to the selected units through `GroupOrders` (in real time, ground and enemy clicks order the primary character; see 011). Disabled or destroyed units drop out of the selection.
- **Why:** The roster gives box selection its candidate list without `Find*` lookups, singletons or a static registry. Keeping selection separate from commands lets AI and scripts order units without any selection.
- **Rejected:** Finding units with `FindObjectsByType` at drag time (global lookup, against 007/009 wiring rules). A static registry of selectable units (global mutable state). Storing selection on the input component (the HUD and later systems need to read it).
- **Implications:** Units spawned at runtime call `UnitSelection.AddToRoster`. Enemies and AI units are `CommandableUnit`s without `SelectableUnit`. Control groups, if wanted, would be saved lists of roster units.

## 011 — Primary character and takeover mode

- **Renamed (2026-10-04, see 012):** `PrimaryCharacter` is now `ActiveCharacter`, and Tab/Shift+Tab can change which friendly it holds. Below, "primary character" means the active character.
- **Decided (Phase 3, 2026-10-04):** One friendly unit is the **primary character** (`FriendlyUnit_1` in `Prototype.unity`). `PrimaryCharacter` (on `Systems`) holds which unit it is and whether **takeover mode** is on. Like `UnitSelection`, it holds state only.
  - **Free mode** (default): WASD pans the camera.
  - **Takeover mode** (V toggles): WASD drives the primary character (camera-relative, through `DirectControlInput` → `CommandableUnit.SetMoveIntent`), and the camera follows it on unscaled time. V works while paused and takes effect on resume.
  - **Real-time clicks** (both modes): ground and enemy clicks order the selection when anything is selected, otherwise the active character; Shift queues. (Until 2026-10-04 they always ordered the active character; the owner found that losing real-time group orders felt like a regression, and one rule for paused and real-time clicks is simpler. The empty-selection fallback keeps "click moves my character" in solo play; Tab selects the character it switches to, so right after a switch the two agree; clicking another friendly selects it without changing who is driven, and Esc restores click-moves-my-character. Rejected: a modifier key for group orders (one more chord to learn) and ordering the selection only when it contains the active character (a selected companion alone would then be unorderable in real time).)
  - **Tactical pause:** the camera is free (WASD pans) and clicks order the selection, which may include the primary character (unchanged from Phase 2).
- **Precedence (primary character only):**
  1. Orders run through the queue as in Phase 2.
  2. Any WASD input while driving clears all of its orders, moves and attacks alike.
  3. Keys win while held.
  4. Releasing them leaves the character idle.
  5. Companions are never affected.
  6. After resume, or after takeover is turned on, keys already held are ignored until Move reads zero (the release gate), so a key held from panning cannot wipe a plan.
- **Why:** One owner (`CommandableUnit`) decides who moves a unit, so direct control and queued orders cannot fight over the NavMeshAgent. The two modes keep WASD for the camera during planning without a separate RTS mode.
- **Rejected:**
  - A separate `ManualControl` component that also drives the mover: two writers to the agent, and precedence split across files.
  - Repeatedly issuing short `MoveCommand`s while keys are held: pathfinding lag, and a command stream the brief ruled out.
  - Cancelling only the current order on takeover: the next queued move would start and fight the keys.
- **Implications:**
  - AI or scripts can use the same move intent later.
  - Switching the active character at runtime is designed in 012; what happens when it dies, in 013 (control passes to the next eligible friendly, or to nobody).
  - If "keys win while held" feels wrong in play, the alternative is that a click suspends the keys until they are released.

## 012 — Active character switching

- **Decided (2026-10-04):** The directly controlled character is no longer fixed. `PrimaryCharacter` was renamed `ActiveCharacter` (file renamed with its `.meta`, so the script GUID and scene wiring survived; renamed fields kept their data through `[FormerlySerializedAs("primary")]`). Any **eligible** roster unit can be the active character:
  - eligible = in `UnitSelection.Roster`, `SelectableUnit` and `CommandableUnit` enabled, GameObject active in the hierarchy, and no `Health` or a living one (`ActiveCharacter.IsEligible`);
  - **Tab** makes the next eligible unit active and **Shift+Tab** the previous one, in roster order, wrapping (`ActiveCharacter.Cycle` → `ControlCycle.NextIndex`). With one eligible unit it stays active; with none nothing changes;
  - Tab works in every mode, paused or not. It changes state only: no orders are issued or cleared and no simulation runs.
- **Handover:** `DirectControlInput` zeroes the old unit's move intent in the same frame. A held move key carries over to the new unit only if it has no orders; otherwise the release gate re-arms, so tabbing onto a unit cannot wipe its plan. The old unit keeps whatever orders it had.
- **Selection follows:** Tab replaces the selection with the new active character, so paused Tab-then-click orders the character just chosen.
- **Camera:** when the active unit changes, the camera glides once to where that unit stands at the switch (same easing as follow, unscaled time); any pan input ends the glide. The point is captured, not re-read, so a glide never turns into a follow in free mode and survives the unit being destroyed. While driving it follows as before.
- **Feedback:** one `ActiveMarker` (`ActiveCharacterMarker`) floats above whoever is active, distinct from the selection ring at the feet. The HUD line names the controlled character.
- **Input:** `Character/CycleCharacter` (Tab) and `Character/CycleReverse` (Shift), both read only by `DirectControlInput`.
- **Why:** the control code should not assume a fixed protagonist; squad members are interchangeable for control. Consumers (input, camera, marker) compare `ActiveCharacter.Unit` with the unit they last saw each frame instead of subscribing to a change event, which catches every source of change and keeps `ActiveCharacter` state-only (as in 006).
- **Rejected:**
  - Separate `NextCharacter`/`PreviousCharacter` actions with a Shift+Tab composite: needs the project-wide "shortcut keys consume input" setting so Shift+Tab does not also fire Tab.
  - Reading `Commands/Modifier` from `DirectControlInput`: two components enabling and disabling one shared action, so disabling either would switch the other's Shift off.
  - Carrying a held key over unconditionally (wipes the new unit's orders) or never (a hitch on every mid-run switch).
  - Leaving the selection unchanged on Tab: paused clicks would order someone other than the character just tabbed to.
- **Implications:** Since Phase 4 the active character's death hands control to the next eligible roster unit (013). Cycling order is roster order. A per-unit "cannot be directly controlled" flag waits for a design need. Right-click stays camera-only; `ClickDragDetector` already separates a right-click from a right-drag, so a future context action can use the click without changing camera control.
- **Amended 2026-10-05 (Phase 6.5, see 024):** a separate `PreviousCharacter` action (LB) now exists for the gamepad; `NextCharacter` (Tab, RB) still goes backward while `CycleReverse` (Shift) is held, so Tab and Shift+Tab are exactly as before and the Shift+Tab composite is still not used.

## 013 — Health, death and the simulation clock

- **Decided (Phase 4, 2026-10-04):** `Health` is the one hit-point implementation for every unit, friendly or hostile (max, current, `TakeDamage(amount, attacker)`, `Damaged`, `AttackedBy`, `Died`). At zero it raises `Died` once and deactivates its GameObject; a `DeathMarker` leaves a flat grey disc where the unit fell. `CommandableUnit` listens to its own `Health`: on death it clears every order and stops, and `Issue` returns false while dead (`IsAlive`). Every existing check (`IsAttackable`, `UnitSelection.CanSelect`, `ActiveCharacter.IsEligible`, `HasUnit`, the HUD) already treats an inactive unit as gone, so death needs no further plumbing.
- **Simulation clock:** `SimulationTime.IsRunning` is the single "may simulation advance this frame" test, true when scaled delta time and time scale are both above zero. It closes the pause-frame leak noted in 007.
- **Controlled character dies:** `ActiveCharacter.RefreshEligibility` (run every frame) moves control to the next eligible roster unit in roster order, wrapping, or to nobody. Takeover mode and the selection are left alone; the dead unit drops out of the selection on its own. With no unit, `HasUnit` is false: WASD pans, no intent is set, clicks order the selection, the HUD says "Controlled: none". `ActiveCharacter` runs at `DefaultExecutionOrder(-200)`, before `DirectControlInput` (-100), so a death never shows as a one-frame `HasUnit` dip that would re-arm the direct-control release gate; a held key carries over to an idle survivor (012 rules unchanged).
- **Why:** one hit-point type keeps the two sides symmetric; deactivating on death reuses the checks the rest of the code already makes; a single clock check is cheaper to reason about than per-component time rules.
- **Rejected:** keeping the corpse as the unit with components disabled (more code and edge cases: clicks on corpses, agents blocking paths); a separate `Damaged` event carrying the attacker (two events is simpler than breaking `HitFlash` and tests); switching selection on death (would wipe a group selection mid-fight).
- **Implications:** a future revive would need the corpse approach instead of deactivation. Corpse markers accumulate until the scene reloads. New simulation components must check `SimulationTime.IsRunning`, not `Time.deltaTime`.

## 014 — One combat path, four deciders

- **Decided (Phase 4, 2026-10-04):** The only way anything attacks is `CommandableUnit.Issue(new AttackCommand(target))`. `CommandableUnit` approaches, repositions when a ranged unit is blind (017), stops in range and faces; `UnitAttacker` applies range, cooldown and damage on scaled time and raises `Attacked`. Four deciders feed it: player clicks (`PlayerCommandInput`, unchanged), `EnemyAI` (015), `CompanionAI` (018, Phase 5) and `AutoRetaliate`: a unit hit while it has **no orders** and no held move intent attacks its attacker. Any order wins (a Move away is a retreat); held WASD wins. Both prefabs carry `AutoRetaliate`.
- **Sides:** `Encounter` (on `Systems`) holds two serialized lists of `Health`, friendlies and hostiles, and computes `Outcome` on read: all friendlies dead → Defeat (checked first), all hostiles dead → Victory, empty sides never resolve. Enemy AI reads friendlies from it; the HUD reads the outcome. No faction system.
- **Attack timing:** damage only in `UnitAttacker.TryAttack`, never per frame; cooldown uses `Time.time`, so it freezes while paused.
- **Why:** player, AI and retaliation share every rule about range, timing, death and target validation, so a fix lands once. `Encounter` keeps "who is on which side" in one place without a faction system the prototype does not need.
- **Rejected:** friendly-only retaliation (a hostile hit from a blind spot would wait for its think tick); a per-unit "hold fire" flag (a future `UnitCommand` if ever wanted); using `UnitSelection.Roster` as the friendly side (ties enemy AI to selection and rules out allied units the player does not control); events on `Encounter` (views read state each frame, as in 006).
- **Implications:** Interact and ranged weapons go through `Issue` the same way. A team concept later replaces the two lists in `Encounter`. `AttackLineView` and `HitFlash` are the only hit feedback and are debug-only. Phase 6 (2026-10-05): still four deciders and one attack path; `EnemyAI` may issue `MoveToCover` ahead of its `AttackCommand`, `UnitAttacker` rolls cover before applying damage and may raise `Missed` (020), and `AutoRetaliate` holds ordered cover (021).

## 015 — Enemy awareness

- **Decided (Phase 4, 2026-10-04):** `EnemyAI` idles until a living friendly is within its detection radius (12 m) **and** in line of sight (`UnitAttacker.HasLineOfSight`, built on `LineOfSight`, 016: one ray from the hostile's eye at 1.5 m to the friendly's centre, blocked by any collider without a `Health` in its parents; units never block sight) **and reachable** (`UnitMover.CanReach`, a complete NavMesh path; added in Phase 5, 2026-10-04). It then issues an `AttackCommand` and leaves the rest to `CommandableUnit`; when that order ends (target dead, unreachable) it looks again on its next think tick (0.25 s, scaled time). Line of sight gates **acquisition only**: a target once taken is followed around corners until it dies. State (`Idle`, `Chase`, `Attack`, `Dead`) is derived from the unit's order, range and health, never stored.
- **Why:** the radius and sight check make approach, positioning and pause matter without a perception system; chasing without re-checking sight avoids oscillation at corners; deriving state keeps one source of truth.
- **Rejected:** always aggressive (every run opens the same way); losing the target when sight breaks (oscillation); target memory, leash, retargeting to a closer unit, cones, alert states (out of scope).
- **Implications:** hiding works before you are spotted, not after. An unreachable friendly is not a target (until Phase 5 it was re-chased every tick). Perception can grow inside `EnemyAI.FindTarget` without touching combat. Sight checks read the physics scene, which only picks up colliders created or moved at runtime after the next physics step (auto sync is off), so geometry spawned at runtime is invisible to hostiles for a frame; the scene's walls are static and unaffected. The sight ray keeps at most 8 hits, so a line crossing more than 8 colliders could miss a wall. Phase 6 (2026-10-05): a ranged hostile may first take nearby useful cover (021); `EnemyState` gains `Cover`.

## 016 — Combat roles and line of sight

- **Decided (Phase 5, 2026-10-04):** `UnitAttacker` carries a `CombatRole` (`Melee`, `Ranged`) next to its range, damage and cooldown; scene instances override the prefab values. `LineOfSight` is the one sight test: a ray from an eye (pivot + 0.5 m, so 1.5 m up) to the target's pivot, blocked by any collider without a `Health` in its parents; units never block. `UnitAttacker.HasLineOfSight`/`CanAttack` wrap it for the unit's own attacks, and `TryAttack` refuses a ranged hit without sight, so no caller can shoot through a wall. Melee ignores sight for hitting; both roles use it for acquisition (`EnemyAI`). A ranged unit stops approaching once in range and never backs away.
- **Why:** two roles and three numbers do not justify a data asset or class system; one sight function shared by attacks, firing positions and enemy acquisition means a change lands once; gating the hit itself keeps the rule out of every decider.
- **Rejected:** a `ScriptableObject` per role or a class system (speculative data); sight checks per caller (duplicated, drift); kiting or minimum range (out of scope, keeps melee hostiles dangerous).
- **Implications:** weapons later become data that fills the same three fields plus the role. The 8-hit buffer cap carries over from 015. Sight is one ray to the pivot, so a half-exposed unit is either seen or not.

## 017 — Repositioning

- **Decided (Phase 5, 2026-10-04):** an attack order runs in three phases inside `CommandableUnit` (`AttackPhase`): **Approach** while out of range (unchanged chase: re-path when the target moves 0.5 m, arriving out of range means unreachable), **Reposition** while a ranged unit is in range but blind, **Attack** otherwise. Reposition searches at most twice a second (`RepositionInterval` 0.5 s) among 16 candidates around the unit's ground point (`FiringPositionFinder`: 8 compass points at 2 m and 4 m, nearest ring first), keeping the first that snaps to the NavMesh (the 2 m `SnapRadius`), is in range and in sight from the eye a unit would have there, and is reachable; the unit walks to the snapped point. A unit walking to a validated firing position commits to it and finishes the walk even if the line clears early, so it ends clear of the corner rather than on its edge; only the walk-at-the-target fallback stops the moment sight returns (ruled during implementation when units stopped on a corner's edge). A walk that has not arrived after 3 s is searched again. After three repositions without firing a shot (since Phase 6 a fired shot, hit or miss, resets the counter: whether it lands is cover, 020), or when no candidate is valid, the unit **walks at the target** until the line clears; at a reachable target's position sight is trivially clear. If that walk ends with the unit still blind (partial path), or no walkable point lies within 2 m of the target, the order **ends** as Approach's does for an unreachable target, so every attack order terminates. Sight is re-checked every frame, so the fallback walk ends as soon as the line clears (a walk to a validated spot finishes first).
- **Why:** the brief asked for a modest, predictable search; the fallback plus the two unreachable exits bound the loop without a planner; keeping the phases in `CommandableUnit` means every decider (player, enemy, companion, retaliation) gets the behaviour for free.
- **Rejected:** candidates around the target or scored by cover (a cover system is Phase 6 or later); searching every frame (16 snaps, rays and paths per blind unit); giving up when no candidate is valid (a ranged unit would stand uselessly behind a wide wall); a 1 m snap radius (candidates in the 0.5 m erosion band beside walls would be rejected exactly where repositioning is needed).
- **Implications:** the search may pick an exposed spot, or one on the far side of an obstacle (nearest by ring, not by travel); cover value would plug into the candidate predicate. The fallback has no standoff, so a ranged unit may end up firing from melee range. `EnemyState` gained `Reposition`, derived from the phase.

## 018 — Companion autonomy

- **Decided (Phase 5, 2026-10-04):** `CompanionAI` (friendlies only, wired to `ActiveCharacter` and `Encounter`, `DefaultExecutionOrder(-150)`) checks every simulation frame whether it is the controlled character (then it stops its own order once and does nothing else) and otherwise thinks every 0.25 s with this priority: **dead** (nothing), **controlled**, **orders** (a current order it did not issue, or anything pending: left alone), **assist** (attack a hostile within 10 m that is the controlled character's target or is already attacking someone; the leader's target first, then the nearest engaged; acquisition only, a running assist is never retargeted), **follow** (beyond 6 m of the controlled character, move to 3.5 m from it on the companion's own side; a running follow move is re-aimed once the leader has moved 2 m and only while the companion is still farther than 3.5 m, so a leader walking into it never pushes it back; the point is snapped to the NavMesh first, else the leader's position), **idle**. It tells its own orders from everyone else's by **remembering the command object it issued**; `Replace` by anyone, `Append` (pending orders), `Stop`, death and direct control all read as "not ours". It only ever `Replace`s or `Stop`s its own order. `CompanionState` is derived on read.
- **Why:** the brief's priority model, implemented as two small methods; command identity needs no change to command data (006) and treats a retaliation like an explicit order (never interrupted by following); requiring an engaged target means companions never start a fight the player did not; the two follow distances and the no-backstep rule stop pacing; running the controlled check before `DirectControlInput` keeps 012's "a held key carries over to an idle unit" true on Tab.
- **Rejected:** a `Source` tag on `UnitCommand` (project-wide change for one consumer); attacking any visible hostile (wakes sleeping enemies); retargeting a running assist to the leader's new target (flip-flopping between engaged hostiles); formations or slots (out of scope); a leash on assist (the player can always order the companion back); interrupting the current follow move when the player queues behind it (the queue semantics of 006 are kept: the queued order runs after it).
- **Implications:** a Shift-queued order waits for a short follow move. Autonomy never overrides explicit orders, even for self-preservation. The controlled character has no autonomy at all; Tab moves that status with it. Later AI (scripts, allied NPCs) can reuse the same component or the same "own command" trick. A player's Stop (X) on a companion more than 6 m from the controlled character is followed by a follow move on the next tick, because there is no hold-position order; a `HoldCommand` is a Phase 6 candidate if the owner wants companions to stay put; Phase 6 did not add one: a companion now stays put only by holding cover it was ordered into (021), and a general hold-position order remains a candidate. Tab onto a companion that is mid-assist stops its own attack as well as a follow move (only its own orders, never the player's). Because acquisition requires reachability, a ranged hostile or companion will not shoot a visible, in-range target standing where no path leads, although an explicit attack order on it would work; revisit when the arena gains islands. Phase 6 (2026-10-05): a companion holding cover it was ordered into does not follow and assists only against a target it can attack from there (021); "engaged" reads `CommandableUnit.AttackTarget`. Follow mode (2026-10-05): the follow step is now gated by the follow flag and the parked/attached state (022), and a Stop now parks the unit, so the remark above that a stopped companion is followed by a follow move no longer holds: it stays where it was stopped until the controlled character walks up to it.

## 019 — Cover points and occupancy

- **Decided (Phase 6, 2026-10-05):** Cover is a set of hand-placed `CoverPoint`s (`Scripts/Cover/`), each a stand position at ground level with a reference to the one collider that protects it and a per-point `hitChance` (0.5); the arena's 20 points are placed in the scene and generated once, like the obstacles. `CoverRegistry` on `Systems` lists them, exactly as `Encounter` lists the sides: a list, not a manager. Every unit carries `UnitCover`, the **only writer of claims**: a **reservation** is made when a `MoveToCoverCommand` starts and lives exactly as long as that order is current (`Replace`, `Stop`, death, direct control, a failed arrival, a vanished point and a walk that makes no progress for 3 s all release it, always after the replacing order has been accepted); an **occupancy** is reached by arriving (`TryOccupy`, within 0.6 m) or by standing still (flat speed under 0.5 m/s) within 0.6 m of an unclaimed point, and lives until the unit is more than 1 m away, the point is destroyed or disabled, or the unit is disabled or dies. `OccupiedByOrder` tells the two apart; only an ordered occupancy changes autonomous behaviour (021). One unit per point: `TryClaim` succeeds only for an unclaimed point or the claimant's own. Standing on a free point is the whole direct-control cover system.
- **Why:** hand-placed points keep the prototype's cover explicit and debuggable; a serialized list matches the project's wiring rule; binding the reservation to the order means no path that clears a queue can leak a claim, and binding the occupancy to standing there means the controlled character, a plain move and a chase all get cover through one rule; the stillness test stops units walking across points from claiming them.
- **Rejected:** generating points at runtime around tagged obstacles (rules per shape and a NavMesh test per face for a benefit hand placement already gives); a cover manager or static registry; reserving at queue time (every queue-clearing path would have to release); tagging commands with their source; `UnitMover.HasArrived` as the stillness test (true while steering); `RequireComponent(Health)` on `UnitCover` (it would chain through `CommandableUnit` and force a `Health` onto every unit, including test units).
- **Implications:** new obstacles need new points. A unit jostled more than 1 m from its point loses it; a unit cannot gain cover while farther than 0.6 m from a point's centre, and an occupant keeps it until it is more than 1 m away. A cover order to a point another unit physically stands on gives up after 3 s. A cover walk also gives up silently after 3 s (`CoverWalkTimeout`) without the flat straight-line distance to the point falling by more than 0.05 m, so a very long detour that moves away from the point for that long would be abandoned; the longest detour in the arena (round `Barrier_I`, about 1.5 s at friendly speed and about 2.1 s at hostile speed) is under the limit, and a path-remaining measure from `UnitMover` is the fix if a real map needs it. `Health` stays optional on every unit. Superseded in part by 023 (2026-10-05): locations are now plain `CoverLocation`s discovered from `CoverSurface` geometry, the hand-placed points and the per-point `hitChance` are gone, and generation is no longer rejected.
- **Direction (owner, 2026-10-05):** missions are meant to be **procedural**, not fixed levels. The hand-placed points above are prototype scaffolding only: once levels are generated, the engine must place cover points itself, including **corner points at the ends of tall obstacles and walls** (protected from the side the wall covers, with sight along the open side, so a unit can peek around the corner to shoot). Until then new obstacles need new points by hand. Deferred, not scheduled: automatic point generation from obstacle geometry, and a real peek behaviour (stepping out of hiding to fire and back), which the Phase 6 brief ruled out of scope. Update (023): automatic placement, including corner locations at the ends of tall walls, is built; a peek behaviour is still deferred. Update (026): missions are now generated (record 026); the engine places the cover itself on every generated mission.

## 020 — Cover and ranged fire

- **Decided (Phase 6, 2026-10-05):** The one directional test is geometric: `CoverPoint.ProtectsFrom` casts a ray from the attacker's eye (pivot + 0.5 m) to the defender's feet (the defender's x/z at the point's height) against the point's obstacle collider alone (`Collider.Raycast`); the obstacle must actually lie between the two. The one defensive effect is **hit probability**: `UnitAttacker.TryAttack` fires at an exposed target as before and at a target in cover with that point's `hitChance`; melee ignores cover. `TryAttack` now means "a shot was fired": `Attacked` is a hit, `Missed` a miss; `ShotsFired` and `Hits` are debug counters; the roll is an injectable `Func<float>` (default `Random.value`). Sight is checked first, cover second: tall geometry blocks the shot entirely, waist-high (0.9 m) geometry lets it through at reduced odds. Points at tall obstacles are therefore hiding spots, points at waist-high walls firing spots. `CommandableUnit` resets its reposition counter on a fired shot.
- **Why:** the ray answers "is the obstacle between" for any shape without a per-point tuning angle; a probability is the smallest hit-resolution rule and keeps every exposed-target test unchanged; the injectable roll keeps combat tests deterministic.
- **Rejected:** an angular cone around the point's forward (redundant with the ray in every arena case, and it denied protection a wide wall gives at steep angles); damage reduction, armour, body parts, criticals, accuracy stats, ballistics.
- **Implications:** the stand point is 0.75 m from the obstacle's face and the ray reaches that face at height 1.125 / D (D = the attacker's distance), so a 0.9 m wall registers beyond 1.25 m and lower obstacles only from farther away (0.6 m: about 1.9 m). Weapons later become data feeding the same four numbers. Since 023 the directional test lives on `CoverLocation.ProtectsFrom` (same ray, same rule).

## 021 — Cover decisions by the player and the AI

- **Decided (Phase 6, 2026-10-05):** A ground click within 1 m of a cover point is a `MoveToCoverCommand` (`CommandResolver`, with the point found by `PlayerCommandInput` through `CoverRules.TryChooseNearest`); Attack on a living `Health` still wins. A group ordered to one point sends the first unit that can reserve it and refuses the rest with their orders unchanged (`GroupOrders` unchanged). A ranged hostile that acquires a target first looks, at acquisition only, for the nearest registry point within 8 m that is unclaimed or its own, protects from the target, lets it attack the target from there and is reachable, and issues `MoveToCover` then `Attack` appended; melee hostiles never look. A companion holding **ordered** cover does not follow and assists only against a target it can attack from where it stands; `AutoRetaliate` applies the same rule; both decide when the own order is issued and never re-examine a running order (acquisition only, as 018). "Whom is it attacking" is read from `CommandableUnit.AttackTarget` by `EnemyAI.Target` and by `CompanionAI`'s engaged and leader-target checks (the current attack's target, else the first pending attack's while a cover order is current), so a hostile walking to cover with its attack queued is engaged for companions and shows its target in the HUD. The cover view shows every point while paused and only claimed points in real time.
- **Why:** reusing the click and `Issue` path keeps input free of cover logic; one unit per marker is the simplest rule the HUD can explain; a hostile that already stands on useful cover must not walk to the next point; without the hold rules the first ranged hit would undo every cover order given to a melee unit; `AttackTarget` gives `EnemyAI` and `CompanionAI` one definition instead of two.
- **Rejected:** moving the rest of a group onto a lattice around the point (slots land on the exposed side) or assigning neighbouring points (squad cover assignment); companion cover seeking; hostile cover re-evaluation while fighting; a mid-order Stop when a covered assister's target leaves range (contradicts 018's acquisition-only model and needs machinery `AutoRetaliate` does not have); cover-aware repositioning (a Phase 7 candidate: feed cover value into `FiringPositionFinder`'s predicate); a selection-aware marker colour (the HUD and the queue view already identify the selected unit's point).
- **Implications:** hostile cover depends on where the target is first seen; from some approaches a ranged hostile finds no useful point and attacks in the open. A covered assister or retaliator whose target leaves its range or sight follows it out of cover through the normal attack phases. Since 023 the hostile search admits only Low locations (corner and tall-face locations wait for a peek behaviour). Since the denser layout (023) the cover click radius is 0.5 m.

## 022 — Follow mode and the magnet

- **Decided (2026-10-05):** Companions no longer walk off on their own after a switch or once the player has placed them; attached companions still follow, assist and retaliate. `ActiveCharacter` holds a **follow flag** (`IsFollowOn`, default on; the F key toggles it through `Character/ToggleFollow`, also while paused) and each `CompanionAI` is **attached** (the state at scene start) or **parked** (`IsParked`). A companion follows (018) only when the flag is on **and** it is attached; the flag gates formation following and nothing else: with it off no follow move starts and a running one of the companion's own is stopped, while assist, explicit orders and ordered-cover holds behave exactly as before. The parked/attached state and the magnet keep updating while the flag is off, and the controlled character is attached by definition (its parked flag is cleared and it ignores the triggers). `CompanionAI.TrackAttachment` decides it every simulation frame, in this order:
  - **A switch of the controlled character** (Tab, Shift+Tab, or the hand-over when it dies) parks every companion farther than the follow start distance (6 m) from the **new** leader; the previous leader counts like any other companion. Companions within 6 m stay attached, because they would not have moved anyway. A switch never attaches anyone and never makes a unit move.
  - **An explicit order parks the unit**: a current order that is neither the companion's own nor a retaliation, or any pending order. Parked is sticky: it is set while explicit orders exist and finishing them does not clear it, so a queued sequence never drops back to Follow between orders and the unit stays where the last one ended.
  - **A Stop parks the unit.** A Stop leaves no order behind, so `CommandableUnit.StopCount` counts every Stop it accepts (also when idle) and `CompanionAI` compares it with the value it saw last frame; the Stops `CompanionAI` issues itself (dropping its own follow move when parked, when the flag goes off or when the unit becomes controlled) are folded into that value so they never park it.
  - **A retaliation does not park.** `AutoRetaliate.IsRetaliating(command)` recognises the exact order it issued; a companion that fights back after being shot should rejoin the squad.
  - **The magnet:** a parked companion with no explicit orders is attached when the controlled character **enters** `magnetRadius` (4.5 m, flat distance, serialized): the controlled character was outside last frame and is inside now, and it is never evaluated on a switch frame. Only the controlled character magnetizes; another companion walking past does nothing. A unit parked while the leader already stands inside the radius stays parked until the leader leaves and enters again.
  - **Attached stays attached**: the magnet radius is for reacquiring parked units, never for detaching attached ones; only a switch, an explicit order or a Stop parks an attached unit.
- **Why:** the owner does not want the squad to start moving by itself after a Tab or after the player has placed units, and wants the controlled character to be able to gather them again by walking up to them. The Tab threshold is the existing follow start distance, so what Tab parks is exactly what would have started walking at the switch. The magnet is an edge because a level ("parked and the leader is inside 4.5 m") would undo a Stop, or an order that ended next to the leader, on the very next frame, contradicting "explicit orders and Stop park". Retaliation is exempt because the owner's list of parking triggers is explicit orders only. The flag leaves assist alone because the owner wants the existing assist behaviour unchanged.
- **Rejected:** a level-triggered magnet (above); parking only on Tab (an explicit order or a Stop would still be undone by following); a per-companion follow toggle (more input and UI for what one flag plus the physical magnet already covers); parking on retaliation; a `Source` tag on commands to tell explicit orders apart (018 already rejected it; the command-object identity trick extends to `AutoRetaliate`).
- **Implications:** parked units never rejoin unless the leader walks up to them, and units the player sends out stay out until then; the HUD marks them `[parked]`. A Shift-queued order behind a companion's own running follow move still waits for that move to finish (018), and the unit is parked meanwhile: the queue is never wiped, so a follow move with something pending behind it is not stopped by parking or by the flag. Known limitations: several leader switches within one pause are compared once, against the final leader (A to B to A parks nobody); a companion that never ran a frame before its first switch is not parked by it; assist is untouched by parked and attached, so after a Tab a companion within 10 m of a hostile that the new leader is attacking (the leader's target is preferred even if that hostile is unaware) can charge it on the next think tick, and whether assist should skip the new leader's target on the switch tick is an open owner question; a unit holding ordered cover shows no `[parked]` marker but does not follow (021). `HoldCommand` stays a candidate; a Stop now does most of what it would do.

## 023 — Procedural cover discovery

- **Decided (2026-10-05):** Cover locations are no longer hand-placed scene objects. A cover location is the plain class `CoverLocation` (position, facing into the obstacle, protecting collider, `Low`/`Tall` height, `Face`/`Corner` placement, hit chance, claim, and for corners a peek direction and peek point). Geometry produces them: obstacles tagged `CoverSurface` (upright `BoxCollider`s, any yaw) are turned into oriented boxes, `CoverGenerator` (pure, EditMode-tested) emits locations, `CoverDiscovery` filters them against the NavMesh and calls `CoverRegistry.Rebuild`, which retires the old locations (dropping their claims) and bumps a version the cover view watches. Face locations: every face of at least 1 m, 0.75 m off the face, spread evenly with a 0.5 m end margin so that every gap between neighbours is at least `spacing` (1.0 m) and under twice that, so no gap can fit another unit one metre wide. Tall walls (top above 1.2 m, at least 2 m long and twice as long as thick) also get four corner locations, 0.35 m inside each end of each long face, with `PeekDirection` along the wall past the end and `PeekPoint` 1.25 m out (kept only if walkable). Update (027): face locations are now generated for Low obstacles only, and a corner is dropped, not kept without peek data, when its peek point is not walkable; see 027. Candidates off the NavMesh, or within `mergeDistance` (0.9 m, below the 1 m minimum gap so float noise cannot merge neighbours) of an earlier accepted candidate **of the same object**, are dropped; points of different objects never remove each other (a corner still beats the face point next to it, because corners are generated first; Update (027): no box has both kinds any more, so this can no longer happen). Update (030): the within-object merge and `mergeDistance` are removed; a candidate is dropped only when its stand point is not walkable, or when it is an exact duplicate (within 0.1 m) of an earlier one of the same object; tall faces no wider than a unit get `Column` locations. Everything downstream is unchanged except its type: reservation, `MoveToCover`, the directional ray test (020), hostile search (021), parking and follow (022). Hostiles choose only Low locations. The view colours by state (a selected unit's destination is green) and shows type by shape (corner: peek arrow).
- **Why:** missions will be procedural (019, Direction), so cover must follow geometry; keeping generation pure and the NavMesh a predicate makes it testable and lets a mission generator call one method (`Discover()`) after it builds geometry and the NavMesh; a plain class lets any source (arena, generator, future tools) supply locations without a scene object; recording peek data now costs a few fields and makes the later peek behaviour an addition rather than a redesign.
- **Rejected:** surfaces that generate and register their own points (no cross-surface dedupe, unclear rebuild order, brings back self-registering points); deriving cover from NavMesh boundary edges (no height or wall-end meaning); keeping a `CoverPoint` MonoBehaviour created at runtime (a scene object per location for no gain); letting hostiles take corner or tall-face locations before peeking exists (they would stand hidden and then leave through the reposition phase).
- **Implications:** supersedes 019's representation (hand-placed `CoverPoint`s, per-point `hitChance`) and its rejection of runtime generation; 019's Direction bullet is done for automatic placement and corners, still open for a real peek behaviour and for non-box geometry. New obstacles need only a `CoverSurface`. Discovery assumes the NavMesh is current, so a procedural mission must build it first. Names are labels (`Cover_<surface>_<N|S|E|W>[Corner]<n>`; Update (030): and `Cover_<surface>_<side>Column<n>` for column locations), not keys; they are unique within one surface (the counter is keyed by side and kind per box) and can repeat only across surfaces that share a name. Hit chance is one generator setting. A rebuild frees every claim; a unit standing still on a location re-claims the equivalent new one, a walking cover order ends silently. A rebuild also clears the "ordered into cover" flag, so a unit that re-claims the equivalent new location by standing still is a chance occupancy and the companion and retaliation hold rules (021) no longer hold it; today discovery runs only at start, so this cannot happen in play. A rebuild while the game is paused leaves units on their retired locations until resume (`UnitCover.Update` does not run while paused), so a second unit could be ordered onto the same spot during that pause; not reachable today. Update (026): the `ProceduralMission` scene rediscovers on every regeneration, but it empties every system first (the pause is resumed in the same step) and replaces every unit, so this paused-rebuild case still cannot happen in play. A corner whose peek point is off the NavMesh stays a corner location with no peek data (only the stand point must be walkable). Update (027): such a corner is dropped, so every corner has peek data. Corner peek data is unused until a peek phase. All fifteen arena obstacles are tagged `CoverSurface`, and the scene's `CoverDiscovery` settings are spacing 1.0 and mergeDistance 0.9 (Update (030): `mergeDistance` is gone and the scenes store `columnMaxWidth` 1.1). Discovery yields 141 locations (the hand-placed layout had 20): `Barrier_I` 14, `Obstacle_CentralWall` 18, `Obstacle_A` 12, `Obstacle_B` 12, `Obstacle_C` 11, `Obstacle_D` 8, `Obstacle_E` 11, `Obstacle_F` 13, `Pillar_G` 4, `Pillar_H` 4, `Crate_J` 8, `Crate_K` 8, `LowWall_L` 6, `LowWall_M` 8, `LowWall_N` 4. Update (027): discovery now yields 46 locations (29 Low, 17 Tall corners): `Barrier_I` 4, `Obstacle_CentralWall` 4, `Obstacle_B` 3, `Obstacle_C` 11, `Obstacle_E` 3, `Obstacle_F` 3, `LowWall_L` 6, `LowWall_M` 8, `LowWall_N` 4, and none for `Obstacle_A`, `Obstacle_D`, `Pillar_G`, `Pillar_H`, `Crate_J`, `Crate_K`. Corner locations before 027: `Barrier_I` 4, `Obstacle_CentralWall` 4 (including the one at about (-3.46, 0, 1.70), 0.84 m from `Barrier_I`'s east end-face location, which an earlier cross-object merge dropped), `Obstacle_B` 4, `Obstacle_F` 4, `Obstacle_E` 3 (its north-west stand point, (3.85, 0, 4.25), is 0.1 m from `Pillar_H` inside the NavMesh erosion zone, so the walkability filter drops it). Update (027): the corner counts above are the numbers before 027; now `Barrier_I` 4, `Obstacle_CentralWall` 4, `Obstacle_B` 3, `Obstacle_E` 3 and `Obstacle_F` 3, and `Barrier_I` no longer has an end-face location for the central wall's corner to sit next to. Because the click rule from 021 (a ground click within `coverClickRadius` of a location orders cover) applies to every generated location, `coverClickRadius` is now 0.5 m so that points about 1 m apart do not turn every ground click near a wall into a cover order; four scene input tests moved their ground click from (-6,0,0) to (-6,0,-1) when the radius was still 1 m. The prototype scene stores the generation settings on its `CoverDiscovery` component (spacing 1, mergeDistance 0.9), so changing the class defaults does not change the arena; a scene test pins the effective gaps. Limitation: points of different objects can lie closer than a unit is wide (seven pairs in the arena are under 0.9 m apart, the closest 0.56 m, `Obstacle_E_W1` and `Pillar_H_S1`); they are separate choices and only one unit can claim each. Update (027): not re-measured; the 0.56 m pair no longer exists because neither tall face location is generated.

## 024 — Native controller input

- **Decided (Phase 6.5, 2026-10-05):** Xbox, PlayStation (DualSense), Nintendo and generic gamepads drive every control state through the Unity Input System, with no Steam Input dependency; keyboard/mouse is unchanged and the player switches freely. Gameplay consumes **semantic actions** in `BlackglassControls.inputactions`; physical bindings live there, in one **binding group per family** (`KeyboardMouse`, `Xbox`, `PlayStation`, `Nintendo`, `Gamepad` = generic).
  - **Active family:** `ActiveInputDevice` (on `Systems`) listens to `InputSystem.onEvent` and applies the family with `InputActionAsset.bindingMask` (and, for a controller, `devices` = that one pad, so a second pad cannot also act). Only *meaningful* input switches it (`InputActivityFilter`): a button press edge, a stick crossing 0.55 (released below 0.35, once per crossing), a trigger past 0.5, any key, mouse movement of 4 px or more or scroll. Drift, held controls and mouse jitter never do. The mask is applied on the next `Update`, so the input that woke a family only wakes it. An unplugged active controller falls back to keyboard/mouse. `InputFamilyClassifier` maps `XInputController` → Xbox, `DualShockGamepad` → PlayStation, `SwitchProController` → Nintendo, other gamepads by USB vendor (Sony/Microsoft/Nintendo) else Generic; `ControllerModel` (DualSense, Switch Pro, Switch 2 …) is kept for later prompt splits and never read by gameplay.
  - **Nintendo** is bound deliberately, not positionally: Confirm is the east button (printed A) and Cancel the south button (printed B); other positions match Xbox. Prompts show the printed labels (`GamepadLabels`, text only, no glyph art; `PromptResolver.GetPrompt(action, family)` derives them from the action's current bindings, so a rebind changes the prompt).
  - **Actions:** renamed (name only, IDs kept) `ToggleTacticalPause`, `QueueModifier`, `Cancel`, `ToggleCharacterControl`, `NextCharacter`; added `PreviousCharacter`, `Look`, `CameraModifier`, `Confirm`, `Attack`, `NextTarget`, `PreviousTarget`, `CursorMove`, and a `UI` map (`Navigate`, `Submit`, `Cancel`, gamepad only, not yet read by any component).
  - **Provisional layout:** left stick = move (driving) / pan; right stick = camera look while the game runs (takeover on or off) / tactical cursor while paused; **RT swaps the right stick's role** (`StickRole`: running + RT = cursor, paused + RT = camera); South = Confirm (with the cursor shown: select / order / cover at the cursor; with the cursor hidden: attack the best hostile, exactly what Attack does), East = Cancel (clear selection, as Esc), West = Attack, North = character control, LB/RB = previous/next character, LT = queue / add to selection (as Shift), Start (Menu / Options / +) = tactical pause, D-pad up/down = follow / stop, D-pad left/right = previous/next target, L3/R3 = zoom out/in, View / Create / - (the pad's select button) = reserved and unbound. Stick dead zones are `stickDeadzone(0.2, 0.925)` processors in the asset, plus a response curve in code.
  - **Tactical cursor** (`TacticalCursor`): a screen-space cursor moved on unscaled time. It resolves a typed `PointerTarget` (`Friendly`, `Hostile`, `Cover`, `Ground`) with the same classification the mouse uses (`PointerTargetResolver`) and snaps to a friendly then a hostile (1.2 m) then a cover location (0.75 m) around the ground point under it. Confirm and Attack call the same `PlayerCommandInput.Act` / `GroupOrders` path as a mouse click; no controller-specific command, combat, movement or cover code exists. Attack picks the cursor's hostile, else the soft target, else the best hostile ahead (`HostileTargets`). The soft target is set only by NextTarget / PreviousTarget (the D-pad cycles living hostiles by distance); hovering a hostile or the best-hostile fallback never sets it, so an Attack does not lock on. Multi-select is LT + Confirm on a friendly (the Shift+click path); there is no box select and no select-all.
- **Why:** the owner wants controller parity as a first-class requirement and rebindable, device-agnostic gameplay; a group mask per family gives per-family bindings (the Nintendo difference) and one-pad-at-a-time for free without a second input framework, and a virtual cursor reuses the mouse's whole order path.
- **Rejected:** `PlayerInput` with control schemes (it owns the actions; every input component here uses `InputActionReference`s); one positional `Gamepad` group (Nintendo would get Xbox's face-button conventions); mouse emulation (poor for a controller); a world-space ground cursor (drifts from the camera, needs separate height handling); separate controller command code; box select with a stick; a sticky snap and a lock-on system (not needed yet).
- **Implications:** a new action needs bindings in all four pad groups (an asset test enforces this) and every binding needs a group (an asset test enforces that too: an ungrouped binding silently dies under a mask). Gameplay code must not name devices or face buttons (a test scans for it). A held button or stick on a pad that is no longer active is ignored until it is released and pressed again. Switching family cancels in-progress actions: `DirectControlInput`'s release gate covers movement keys and sticks, and `PlayerCommandInput` ignores a cancel while the mouse button is still physically held, so a family switch never issues a click or a box select. On keyboard/mouse the asset's `devices` restriction is left unset (the group mask alone excludes controller bindings); only a controller family restricts `devices` to its one pad. Rebinding works through the standard Input System API (`ApplyBindingOverride`, `PerformInteractiveRebinding`, JSON save/load; covered by a test); there is no rebinding UI yet.

## 025 — Combat archetypes and abilities

- **Decided (Phase 7, 2026-10-06):**
  - **Archetypes:** `CombatArchetype` ScriptableObjects (role, range, damage, attack interval) assigned on `UnitAttacker.archetype` and applied at `Awake`; the inline fields remain the fallback, so existing units and tests are unchanged. The role still decides line of sight and cover (melee needs neither and ignores cover; ranged needs sight and is affected by cover). Three exist: Melee (2 / 25 / 1.0 s), Ranged (8 / 15 / 1.0 s) and Marksman (16 / 40 / 2.5 s); `FriendlyUnit_1`/`_2`/`_3` use them. Hostiles keep inline values. There is no inventory or equipment.
  - **Abilities:** `AbilityDefinition` is an immutable ScriptableObject (target mode Unit or Ground, side Hostile or Friendly, range, line-of-sight flag, cover rule Applies or Ignored, cooldown, effect Damage or Heal, amount, radius). An ability definition's target side is derived from its effect (Damage => Hostile, Heal => Friendly) in `AbilityDefinition.Create` and `OnValidate`, so no authored asset can make an ability hurt its own side. The target side and the effect are also derived when read (a ground ability is always damage), so a hand-edited asset cannot hurt its own side in a build either. `UnitAbilities` on each unit holds up to four definitions and, per slot, the **scaled** time at which it is ready again, so cooldowns freeze while paused and belong to the unit (they survive control-mode changes and character switching, and two units sharing a definition never share a cooldown). Mutable state is never stored in an asset. Prototype abilities: Aimed Shot (single target, needs sight, cover applies), Blast (ground area, needs sight to the point, ignores cover) and Mend (heal a friendly, itself included, no sight needed).
  - **One validation:** `AbilityRules` and `UnitAbilities.Check`, in this order: caster alive, ability known, target (or position) valid and on the right side, cooldown, range (flat, inclusive), line of sight. The preview, `Issue` and execution all use it. Failures are typed (`AbilityFailure`), kept on the unit (`LastFailure`) and raised as events; an expected failure never writes to the Console.
  - **Command integration:** `AbilityCommand` rides the existing queue (Replace and Append, group orders, Stop, companion park rules all unchanged). It is instant. When it would start now `Issue` checks everything; behind other orders it checks only who and what (the caster will have moved on). It is validated again on the first **running** frame, before steering is considered, so nothing fires while paused and a held move key cannot drop an ability that direct control just issued (update, 029 and ruling R10: this holds for an ability usable at once; one that would first have to walk is refused while the unit is steered). A failure ends the order without a cooldown and the queue moves on, so a unit never sticks. No auto-approach: an out-of-range ability fails (Attack keeps its approach). Update (029): no longer true. An ability whose only problem is range or line of sight is accepted and the unit walks into position first, with the attack's approach and reposition steps; every other failure still refuses it at once.
  - **No friendly fire:** area damage hits only units hostile to the caster (`Encounter.OpponentsOf`); no ability can hurt its own side. The owner does not want friendly fire in the game.
  - **Cover is an explicit rule per ability**, not an accident: Aimed Shot uses the same hit-chance roll as basic ranged attacks (`UnitAttacker.RollHit`), Blast ignores cover.
  - **Targeting:** `AbilityTargeting` arms a slot of the caster's abilities (the caster is the first eligible selected unit, else the active character, also while paused), resolves the pointer every frame (the mouse through `PointerTargetResolver`, the controller through the Phase 6.5 `TacticalCursor`, which is reused, not duplicated), and exposes a live preview. While armed, `PlayerCommandInput.Act` hands a click or Confirm to it, Cancel disarms before it clears the selection, and a change of caster or its death disarms. The cursor gets `Aiming` (the right stick is the cursor's whatever else would own it, `StickRole`) and `SnapTo` (hostile, friendly or none for an area).
  - **Input:** semantic actions `Ability1`-`Ability4` and `AbilityMenu`. Keyboard: keys 1-4. Pads (every family): hold the right trigger and press a D-pad direction (up, right, down, left), as `ButtonWithOneModifier` chord bindings; Confirm/Cancel/queue modifier are the existing ones. Input System shortcut consumption is **off** by default in 1.20, so `AbilityMenuGate` disables the plain D-pad actions (Stop, Follow, previous/next target) while the menu trigger is held and gives back exactly what it took. Select/View/Create stays reserved and unbound.
  - **Debug only:** `AbilityTargetingView` (range circle, aim ring, line, green/red; amber since 029), `AbilityBarView` (slots, prompts, cooldowns, preview line, orders, last failure), the unit label shows the archetype name, `CommandQueueView` draws ability orders.
- **Why:** the owner wants the first real combat choices without an inventory, stats or a scripting layer; immutable data plus a small per-unit runtime keeps the framework smaller than the future feature list while a grenade, a burst or a buff stays a new field or effect, and the existing command queue, pause, cursor, LOS and cover are reused instead of duplicated.
- **Rejected:** one MonoBehaviour per ability (duplicated targeting, cooldown and validation); a strategy ScriptableObject per effect (more than three effects need); migrating the basic Attack onto abilities now (it would rewrite working combat, AI and most of the existing tests); a separate tactical ability scheduler (the queue already orders and parks); auto-approach or projecting the caster's future position for queue-time checks (the brief says fail cleanly; projection needs path prediction; update (029): auto-approach was adopted at the owner's request, projection is still rejected); cooldown state on the ScriptableObject; a radial menu or a mode that remaps LB/RB (code that knows modes); turning on Input System shortcut consumption project-wide; friendly fire.
- **Implications:** a new ability is a new `AbilityDefinition` asset when it fits the fields, otherwise a new `AbilityEffect` handled in `UnitAbilities.Apply`; every new action still needs bindings in all four pad groups (the asset tests enforce it); gameplay code must not name devices or buttons. The cursor's `Aiming` and `SnapTo` are readable by anyone but have internal setters, used by `AbilityTargeting` only. A queued ability is judged from where the unit ends up, while the planning preview judges from where it stands (it says so while the queue modifier is held).
- **Known limitations:** one caster per cast and four slots (no groups, pages or hotkey rebinding UI); instant casts (no wind-up, interruption or projectile); enemy AI does not use abilities; the basic Attack is not an ability yet (a Phase 8 question: one action framework for both); while armed the camera cannot be moved with the right stick; the chord ergonomics (right index finger on the trigger, thumb on the D-pad) are untested on hardware (every pad test uses simulated devices). While an ability is armed, pressing the pad's Attack button disarms it and then attacks the best hostile (the owner may prefer Attack to be ignored while armed). The scene's FriendlyUnit_2 is the Marksman, so that companion now stands off at 16 m.

## 026 — Procedural missions

- **Decided (Phase 8, 2026-10-06):**
  - **Pipeline and ownership:** `MissionDirector` (one component in the new `ProceduralMission` scene; `Prototype` is untouched and stays the hand-built regression arena) runs a coroutine: teardown, wait one frame, then per attempt layout (pure `MissionGenerator`), geometry (`MissionBuilder`), runtime NavMesh, navigation validation (`MissionNavigation`), cover discovery, spawn (`MissionSpawner`), camera framing, `State.Ready`. Everything generated lives under one `GeneratedMissionRoot` with two children: `Geometry` (floor, walls, obstacles, the `NavMeshSurface`) and `Actors` (every unit). Everything persistent (input, `TacticalPause`, camera, HUD, controller cursor, `Encounter`, `UnitSelection`, `ActiveCharacter`, `CoverRegistry`, `CoverDiscovery`, `AbilityTargeting`, the debug views) is never created or destroyed by a mission, only reset and refilled. States are `Idle`, `Generating`, `Ready`, `Failed`; a request while `Generating` is refused with a warning. The generator settings are a plain `[Serializable]` `MissionSettings` on the director (`Validated()` returns a clamped copy, `Describe()` prints every field); the squad and hostile kinds are `FriendlySlot`/`HostileSlot` data (prefab, archetype, abilities; hostile `i` uses slot `i mod slots`), and the director sets `friendlyCount` from the number of friendly slots.
  - **Seed and determinism:** `SeededRandom` is SplitMix64 (a class, so a copy cannot fork the stream), used instead of `System.Random` and `UnityEngine.Random`; attempt *n* of seed *s* gets `ForAttempt(s, n)`, so a seed gives the same layout however many earlier attempts failed. Every layout decision is an integer tile coordinate (1 tile = 1 m); floats appear only when the builder converts tiles to world positions. `MissionLayout.Hash` (FNV-1a over the mask, rooms, connections, boxes, spawn regions and spawns, with a count before every list) is compared by tests: same seed twice, different seeds differ, and the golden seeds 12345, 1 and 2 are pinned (the values live in `MissionGeneratorTests`; change them deliberately when the algorithm changes). A test seeds `UnityEngine.Random`, generates, and checks the global sequence is untouched, so `UnitAttacker.RollHit` stays isolated. A new random seed comes from `Environment.TickCount`, never from `UnityEngine.Random`.
  - **Layout model:** rooms on a coarse grid (default 4x3 cells of 14 m, 6 rooms grown as a connected set, each room 7 to 10 tiles a side and inset at least 2 tiles from its cell), a spanning tree of corridor strips (3 m wide; each strip lies entirely in the gutter between two rooms and touches both room edges, only its lateral extent lies inside the overlap of the two rooms' extents, and the door gap it leaves in each room wall is exactly as wide) plus up to `extraLoops` extra connections, rasterised to a floor mask. **Wall-ring rule:** wall tiles are the void tiles 8-adjacent to a floor tile, merged into boxes by a deterministic greedy rectangle cover (`RectCover`, also used for the floor), so a room frame becomes a few long 3 m by 1 m boxes, a door gap ends a wall in a clean end face, and `CoverGenerator` turns those ends into corner locations. Update (031): a strip's lateral edge relative to each room's edge is either flush or at least 2 tiles inside it, never exactly 1 tile, for both rooms and both sides (a 1-tile step leaves a 1 m wall stub beside the mouth with no corner point); the start is drawn from the valid starts only, and a pair with no valid start is not a legal connection. Update (032): the walls no longer use the greedy cover: wall boxes are the maximal straight runs of wall tiles in both directions, overlapping at junction tiles, so each straight wall face ends at the visible corner (the floor still uses `RectCover.Decompose`).
  - **Obstacles:** per room up to `bafflesPerRoom` baffles (tall, 3 to 5 tiles by 1) and a 50% chance of one pillar (1x1, tall), then low walls (3x1) and crates (1x1) at 1 m high until `lowCoverDensity` per 100 m2 of floor is reached or the tries run out. An obstacle keeps a **clearance of 2 tiles** to every other obstacle and to every corridor strip (so no obstacle narrows a door) and, for tall obstacles, to the room walls. **Low cover may stand 1 tile from a room wall** (the second half of its 40 tries; the first half keeps the 2-tile gap) but never within 2 tiles of a corridor. Update (030): a 1-tile gap is never used, because a unit does not fit in it on the eroded NavMesh; low cover keeps 2 tiles to every room wall, except that in the second half of the tries a low wall may touch one wall with its short end (end-on); see 030. Each placement is rejected if the 4-connected flood fill over the free floor tiles would split.
  - **Spawn rules:** the friendly room and the main hostile room are the pair with the greatest room-graph distance (BFS; ties by the seeded RNG; the pair is swapped by a coin flip); hostiles fill the main room's region first and then the room farthest from the friendly room, so at most two rooms. A region is its room shrunk by 1 tile; spawn tiles are shuffled and accepted when more than 1 tile from every obstacle, at least 2.5 m from every chosen unit and, for hostiles, at least `minTeamSeparation` (16 m, straight line) from every friendly. If a region cannot supply all its points the attempt fails. Update (033): generated missions also get up to `guardCount` (default 2) guard hostiles in the terminal room, so a mission's `Hostiles` is `layout.HostileSpawns` plus the guards.
  - **Two validation levels and the bounded retry:** (1) grid level in the pure generator: the flood fill above after every placement and once more on the final layout (every free floor tile reachable). (2) NavMesh level after the build: the mesh is not empty and covers at least 30% of the floor area (a sanity check: the eroded mesh of a cluttered room is legitimately well below the floor), the first friendly spawn is on the mesh, and a complete path leads from it to every room centre and every spawn point; the spawner then snaps every point to the mesh within 1 m and checks it for geometry with `Physics.CheckCapsule`. Any failure ends the attempt and the next one starts (`maxAttempts`, default 20, clamped 1 to 100). Exhausting them sets `State.Failed` and logs **one** `LogError` with the seed, `Describe()` and each attempt's reason; no units are spawned and the scene is empty.
  - **Runtime NavMesh:** a `NavMeshSurface` on `Geometry` (collect Children, physics colliders, default agent type) builds synchronously after `Physics.SyncTransforms()` (auto sync is off); every obstacle cube has a Not Walkable `NavMeshModifier`, so no walkable island forms on a wall or crate top. `Blackglass.asmdef` references `Unity.AI.Navigation` (already in the manifest, no new package). Geometry is `GameObject.CreatePrimitive` cubes, each obstacle a `CoverSurface`, with optional shared placeholder materials.
  - **Cover:** `CoverDiscovery.Discover(Transform root, Func<Vector3,bool> isReachable = null)` collects `CoverSurface`s under the mission's `Geometry` only and drops locations that fail the existing walkability test or the reachability test (a complete path from the first friendly spawn); the no-argument `Discover()` is unchanged. There is no second cover representation: AI, `MoveToCover`, the cover view and the controller cursor consume the same `CoverLocation`s (023), and tall-wall ends give `Corner` locations. The number of dropped locations is not reported (the generator also asks about peek points, so the count would mislead).
  - **Regeneration lifecycle:** teardown runs first, also on the first generation. Order: `CoverRegistry.Rebuild(empty)` (retires every location and claim), `Encounter.Initialize(empty, empty)`, `UnitSelection` cleared and re-initialised empty, `ActiveCharacter.SetUnit(null)`, `AbilityTargeting.Disarm()`, `TacticalPause.Resume()`; then each tracked unit's `DeathMarker.LastMarker` is destroyed (**death markers are scene-root objects that outlive their unit**, so destroying the root alone would leave them); then `GeneratedMissionRoot` is destroyed (deferred `Destroy`) and the coroutine waits one frame so the old NavMesh and colliders are really gone. `NavMeshSurface.RemoveData` removes only the instance, so the surface's `NavMeshData` is destroyed explicitly (otherwise every bake would leak one data object per regeneration; a test pins that the number of `NavMeshData` objects does not grow over repeated regenerations). A failed attempt is destroyed immediately so the next attempt cannot see its NavMesh. `Clear()` and `OnDisable` call `CancelRun` (`StopCoroutine`), so a clear during `Generating` cannot leave two runs or an orphaned mission; the only yield comes before any build or spawn, so stopping never leaves a half-built mission. Units are spawned with `Actors` inactive and wired before activation, and `MissionSpawner.TrySpawn` refills the persistent systems before it activates `Actors` (roster and encounter, selection, the first friendly as active character, takeover off, follow on); the director then frames the camera. Teardown deactivates the old mission root before the deferred `Destroy`, so nothing in it can run, or leave a death marker, during the frame the destroy is pending. An exception inside an attempt is caught and recorded as a failed attempt (`attempt N: exception: ...`) instead of leaving the director stuck in `Generating`.
  - **Developer controls:** F6 regenerates the same seed and F7 a new seed, as `RegenerateSame`/`RegenerateNew` in a keyboard-only `Developer` input map read by `MissionDeveloperInput`, which calls the director and nothing else (the pad asset tests use an explicit action list, so they needed no change). A specific seed is typed into the `seed` field of the director's Inspector in Play Mode, then F6. Update (after Phase 8): at Play the scene opens on a fresh clock-based seed, not the serialized 12345 (`newSeedAtStart`, default on; written back to `Settings.seed`, so the HUD and Inspector show it and F6 repeats it); with the flag off the Inspector seed is used. The scene tests wait for that first mission and then call `Generate(12345)`, so they keep their deterministic layout. `MissionDebugView` (IMGUI text, top right) and `MissionGizmoView` (rooms, graph, spawn regions, bounds) are debug only.
  - **Camera:** `TacticalCameraController.SetBounds(Rect)` replaces the fixed clamp with the mission bounds plus a margin (`cameraMargin`, 2 m) and `FocusOn(Vector3)` snaps to a point without gliding; the director calls both after every generation.
  - **Unit wiring:** three narrow internal methods, `CompanionAI.Wire`, `EnemyAI.Wire` and `UnitCover.Wire`, set only the references a spawned unit needs, so prefab-tuned values are not overwritten by `Initialize` defaults.
  - **Measured totals:** EditMode 555 and PlayMode 553 tests, all green (baselines 517 and 513).
- **Why:** the brief makes missions procedural and requires every existing system (direct control, pause, queues, companions, AI, line of sight, cover, abilities, both input families) to work on them unchanged, so the generator produces only geometry and spawn points and the persistent systems are reset, not rebuilt. An integer layout with a private PRNG makes a seed reproduce a mission after any runtime or Unity upgrade and leaves combat randomness alone. Grid rooms with corridors across fixed gutters guarantee that connections and door gaps exist by construction, and the wall ring plus greedy rectangle cover gives few boxes and exactly the wall ends cover discovery needs for corners. Two validation levels keep the cheap pure check inside the generator (testable over hundreds of seeds) and the real NavMesh check where the NavMesh exists. A bounded retry with a reproducible failure message means a bad seed can never hang or hide. A new scene keeps the `Prototype` tests as a hand-built regression arena, and keyboard-only developer keys keep a click or a digit from reaching gameplay input.
- **Rejected:** BSP rooms with routed corridors (more code and degenerate corridors for no prototype value); hand-made room templates (not procedural); `System.Random` or `UnityEngine.Random` for layout (not stable across runtimes, or global state shared with combat); converting `Prototype` in place or toggling an arena inside it (rewrites about 36 tests, or two worlds in one scene); a second cover representation for generated missions (it would violate 023; the generator reads the same boxes); baking the NavMesh into the scene or using the low-level `NavMeshBuilder` API (not runtime-generated; the package surface is the simplest supported route); clickable IMGUI debug buttons and a typed-seed text box (a click would also reach `PlayerCommandInput` as an order and digits would fire abilities 1 to 4); keeping the old mission when generation fails (extra state for a prototype); a ScriptableObject for the settings (no sharing need yet).
- **Implications:** a new mission feature is a change to the pure generator plus, if it adds geometry, a `MissionBox` kind. Anything it puts in the scene must live under `GeneratedMissionRoot` or be removed in `Teardown`, and any new persistent system that remembers units must be emptied in `ResetSystems`. Changing the algorithm changes the golden hashes (re-pin them once, deliberately). The scene tests depend on seed 12345's layout through searched positions, not fixed offsets. Failed attempts build nothing in the scene, so retries cost only CPU (seeds 1 to 200 all generate within 6 attempts, the whole set took about 0.2 s in EditMode in a one-off measurement). `Prototype` and its cover, scene and input tests are unchanged. Update (033): a mission feature may also be an objective (a `MissionObjective` plus content in `MissionContent`, see 033), and the content step runs before the NavMesh bake when the feature is solid geometry.
- **Retained regression seeds** (default settings; 12345, 1 and 2 are pinned by golden hashes; 12345 is the seed the scene tests regenerate (the scene itself draws a clock seed at Play) and seed 2 also needs 2 attempts): 163 (6 attempts, the most of seeds 1 to 200); 196 (5 attempts); 46 (3 attempts and the most tall obstacles, 6 baffles and 4 pillars; seed 5 has the same count in 1 attempt, plus 10 low objects); 53 (fewest tall obstacles, 5 baffles and no pillar); 158 (also 5 baffles); 110 (most low-cover objects, 13; seed 141 also has 13); 41 (fewest low-cover objects, 1; seeds 24 and 68 have 2); 42 (smallest team separation, 16.28 m, a hair over the 16 m limit); 149 (second smallest, 16.55 m, after 2 attempts). Measured over seeds 1 to 200 on the final generator: attempt 1 succeeds for 131 (65.5%), 45 seeds need 2 attempts, 16 need 3, 6 need 4, one needs 5 and one 6. Update (030): the low-cover rule changed every layout that used the relaxed tries (the golden hashes were re-pinned), so the per-seed figures in this bullet are from before 030; now attempt 1 succeeds for 166 of 200 (83%), 23 need 2, 9 need 3 and 2 need 4. Update (031): the strip rule changed every layout (golden hashes re-pinned); now attempt 1 succeeds for 152 of 200 (76%), all 200 seeds generate within 5 attempts, low objects per mission median 3. Update (032): the wall boxes changed (golden hashes re-pinned); walls feed no random draw, so the attempts, seeds and figures above are unchanged.
- **Known limitations:**
  - **Low cover is modest.** `lowCoverDensity` is effectively a ceiling, because the clearance rules leave little room once the tall obstacles stand (Update (030): still true, and more so: with the 2-tile wall gap plus end-on walls only, the median is 3 objects per mission). Because low cover may stand 1 tile from a room wall (the 2-tile clearance alone starved it to about 3 objects per mission) the median is 7 low objects per mission (3 before), and 3 seeds of 200 have fewer than 3. That gives about 27 `Low` cover locations against about 290 `Tall` ones, so about 90% of locations are tall, and hostiles choose only `Low` cover (023), so enemy cover use is limited. Update (027): tall obstacles no longer have face locations, so those numbers are before 027. Measured after it (`MissionBuilder` plus `Discover`, reachable only): seeds 1 to 8 and 12345 give 11 to 42 `Low` locations and 53 to 65 Tall corners (seed 1: 11 Low and 59 corners, down from 283 Tall locations), so about 15 to 40% of locations are `Low`, and the tall ones are all wall-end corners. About 59% of low objects stand 1 tile from a wall; that gap is too narrow for the NavMesh agent, so cover discovery drops the unreachable points there and the pocket is dead space. Update (030): those numbers counted objects, not useful cover: the 1-tile objects' wall-side points were dropped and an object lying along a wall offers points that face the wall, so useful low cover was about 3 objects per mission. Now no low object stands 1 tile from a wall or flush along one; each is free-standing or a low wall touching a wall end-on, so every object is useful: seeds 1 to 200 give a median of 3 (mean 3.39, from 0 to 9), 33 seeds have fewer than 2 (decision 030).
  - **Attempt-1 success is 65.5%** (83.5% when low cover needed 2 tiles of clearance to walls; Update (030): 83% with the end-on rule); every failure is a spawn-fit failure (obstacles in the spawn rooms remove spawn tiles). Options for later: choose the spawn rooms before placing obstacles, or more placement tries spread over the rooms plus the 1-tile wall gap while keeping the 2-tile gap between low objects (measured slightly better: median 8, 60 of 60 seeds with at least 3 low objects, 136 of 200 on attempt 1). Update (031): 76% (152 of 200) with the strip rule; 14 of the 48 attempt-1 failures are now tree-completion failures, the rest were spawn-fit failures and one hostile-spacing failure.
  - **Walls hide the floor behind them.** Walls are 3 m high and the tactical camera (pitch 55) cannot see the floor within about 2 m behind a wall. With seed 12345 the squad spawns 1.5 m from a 3 m wall: a click or a pad Confirm there hits the wall top and gives no order and no feedback (the pointer resolves any non-unit collider as ground, and the move is refused because no NavMesh lies near a point 3 m up). **Owner decision needed:** wall fade, spawn placement away from walls, camera framing or pitch for generated missions, or letting ground clicks pass through wall tops. A test "the floor around the squad spawn is clickable from the default framing" should be added once this is decided.
  - `MissionNavigation.NavMeshArea` sums the triangles of every active NavMesh (documented; the later path and snap checks still catch an empty mission mesh). The layout hash omits box names and the attempt number. A failure after a regeneration leaves an empty scene, by design (teardown first, no "keep the old mission" path; the seed must be set again to retry).
  - One floor level, axis-aligned whole-metre geometry, one mission shape family, no doors that open or close, no objectives beyond the existing win condition. Corner cover still has no peek behaviour (023) and enemy AI still does not use abilities (025). The camera may show the void around the mission.
  - The controller scene test uses `FocusOn` to bring the cursor to its targets, because the wall-occlusion limitation above can hide a target. `MissionGenerator.cs` is 670 lines (obstacle placement and spawns could be split out). Small gaps left open: a few weak test assertions, no test of the "1-tile pocket never on a path" claim, `MissionDeveloperInput` does not null-check its director, `Initialize` after enable leaves it unsubscribed.
  - **Enemy placement is spatial only** (the main hostile room and the farthest room): there is no encounter director, so nothing paces, groups or triggers the hostiles.

## 027 — Cover only where it covers

- **Decided (2026-10-06):** One rule in `CoverGenerator`, everywhere (the generated missions and the hand-built `Prototype` arena), with no setting to turn it off. Owner's words after reviewing a generated mission: cover points should exist only where they can provide cover; the corner of a room is not cover, and a long wall has none along it, only at its ends where it opens into another space; low obstacles can be crouched behind anywhere.
  - **Low obstacles** (box height at or below `lowMaxHeight`, 1.2 m): unchanged. Face locations along every usable face, merge and spacing rules as in 023. They never had corners. Update (030): the merge is gone (see 030).
  - **Tall obstacles:** no face locations at all. A tall wall (at least 2 m long and twice as long as thick) gets its existing corner candidates, one per end of each long face, 0.35 m inside the wall end, and a candidate is kept only if its **peek point is walkable** (`isWalkable(stand + along * peekDistance)`) as well as its stand point. A closed room corner, a T or L junction where the wall end runs into another wall, an end at the edge of the map or against an eroded NavMesh edge therefore gets nothing. Every Tall location is thus a `Corner` with `HasPeek`.
  - **Tall pillars and stubs** (length under 2 m or less than twice the thickness: `Pillar_G`, `Pillar_H`, `Crate_J`, `Crate_K`, `Obstacle_A`, `Obstacle_D` in the arena, pillars in missions): no locations. Assumption stated to the owner: a 1 m pillar does not hide a unit; tall crates and stubs get nothing. Update (030): reversed by the owner for faces no wider than a unit: a 1x1 mission pillar gets a `Column` location on each face and a stub or thin wall one beyond each end cap no wider than 1.1 m; the arena's 1.5 m pillars, the 2 m crates, `Obstacle_A` and `Obstacle_D` still get none. Update (031): the end caps exist only on free-standing walls and baffles (room-frame wall ends have none), and a stub gets one only if a unit can go round it.
  - **Unchanged:** `CoverLocation` and its representation, hit chance, stand offsets, merge distance, spacing, the NavMesh walkability filter, `CoverDiscovery` (and its reachability filter), hostile selection (hostiles choose only Low, so they never used tall faces), the cover view, and `CoverGenerationSettings` (no new field). Update (030): `mergeDistance` removed, `columnMaxWidth` added.

## 028 — Spawn hold for companions

- **Decided (2026-10-06):** Companions of a generated mission start **held**: `MissionSpawner.TrySpawn` calls `CompanionAI.HoldUntilLeaderMoves()` on every friendly. A held companion starts no follow move (one more condition next to the follow flag and `isParked` in `CompanionAI.Think`), however far it stands from the controlled character, until the controlled character first moves. "Moves" is measured in `TrackAttachment` (every simulation frame, so never while paused): the controlled character's flat speed from its position change between frames is above 0.5 m/s (the figure `UnitCover` uses for standing still), or its `MoveIntent` is non-zero (a held move key). The first frame, and the frame of any change of the controlled character, only seed the last position, so a Tab does not release the hold: the new leader has to move. A held companion that becomes the controlled character is no longer held. After the release the normal rules apply (attached companions beyond 6 m follow, parked ones do not). Assist, retaliation, explicit orders, parked and attached bookkeeping, the F follow flag and ordered-cover holds are unchanged while held. `IsHeld` is public; the HUD marks a held companion `[held]`. The `Prototype` scene is untouched (its units start close).
- **Why:** owner: units spawned a little apart because of wall placement used to "squad up" and walk to the first unit at once; there should be no movement until the main unit starts to move, an exception to the magnet and follow range just at spawn. It is state on the companion, released by an observable fact (the leader moved), so it needs no timer and no scene wiring.
- **Rejected:** a timer (the player may wait and plan as long as they like); parking the companions at spawn (parked units need the magnet to rejoin, which would change the squad's behaviour for the whole mission); holding in `MissionDirector` or `ActiveCharacter` (the rule is companion autonomy, 018); releasing on the first Tab (the owner's wording is about the main unit moving).
- **Implications:** the leader's first step releases the whole squad at once (each companion measures the same leader). A companion that is spawned and then warped (tests, tools) stays where it is until the leader moves. A Tab before the first move parks the held companions that stand farther than 6 m from the new leader (decision 022); when the new leader moves they are released but still parked, so they follow only after the magnet re-attaches them. Known limitation: a leader that is pushed by another unit above 0.5 m/s releases the hold as well; nothing triggers it at spawn today.

## 029 — Abilities approach their target

- **Decided (2026-10-06, amends 025):** owner: "if I select to use an ability and it's out of range or there's no line of sight, the unit should queue up moving into range to execute. Same as if I clicked an enemy the unit would move to attack."
  - **Accepted, not refused.** `AbilityRules.IsApproachable` is true only for `OutOfRange` and `NoLineOfSight`. `CommandableUnit.Issue` (when the order would start now) goes through `UnitAbilities.CanOrderNow` (it replaces `CanStartNow`): the full check passes, or fails only on those two, and the order is accepted without recording a failure. Everything else is refused at once with its reason, as before: caster dead, ability unknown, no or dead or inactive target, wrong side, no position, `OnCooldown`, no `UnitAbilities`. The validation order in `AbilityRules` is unchanged, and the cooldown is checked before range, so a unit never walks anywhere for an ability that is still cooling down (owner assumption: it is refused with the usual reason). `UnitAbilities.Check` and `TryUse` still report and refuse range and sight: `TryUse` is the instant primitive, the walk lives in `CommandableUnit`.
  - **The ability order carries the phases.** On every running frame `RunAbilities` checks the current ability first (before steering, as in 025): usable, it fires (`TryUse`) and the queue moves on; refused for any other reason, `TryUse` records the reason and the queue moves on; out of range or out of sight, it hands over to `UpdateAbility`, which runs after the move-intent check, so a held move key drops the walk like any other order. `AbilityRules.ApproachPhase` picks the step: `OutOfRange` walks toward the aim (`Approach`), `NoLineOfSight` searches a firing position (`Reposition`). The unit fires on the first frame the ability is usable, so it stops at the edge of range or as soon as the line clears (an attack instead finishes a walk to a validated firing position, 017; a one-shot ability has no reason to). `CommandableUnit.AbilityPhase` exposes the step (`AttackPhase.Approach` / `Reposition`, `None` otherwise); `AttackPhase` stays attack-only, so `EnemyAI` and the HUD are unaffected.
  - **Shared, not duplicated.** The attack's `Approach`, `Reposition`, `SearchFiringPosition`, `IsFiringPosition` and `StillWalking` now take a small private `Aim` (an attack's target, or an ability order plus the reason it cannot be used yet) instead of a `Health`. The only branch is the range-and-sight test from a candidate pivot: `UnitAttacker.CanAttackFrom` for an attack, `UnitAbilities.CanUseFrom` for an ability (the ability's own range, and sight only when it needs it; a ground point is judged as `Check` judges it, a unit standing there, 1 m up, through the new `UnitAttacker.HasLineOfSightToPointFrom`). The constants (re-path at 0.5 m, a search at most every 0.5 s, 16 candidates, 3 s per reposition walk, three repositions then the walk at the target) are the attack's. `AttackCommand` behaviour and its tests are unchanged.
  - **Ground and unit targets.** A unit target (Aimed Shot, Mend) is followed as the attack chase does; Mend needs no sight, so it only walks into range. A ground target (Blast) is walked toward until it is in range and, if required, visible.
  - **Giving up.** The order ends, the reason is recorded on the unit (`LastFailure`, `Failed`), no cooldown is spent, nothing is written to the Console as an error, and the queue moves on, when: the target dies, vanishes or turns invalid (the per-frame check refuses it: `TargetDead`, `NoTarget`), a refusal such as `OnCooldown` appears; the place cannot be reached (`Approach` arrives still out of range, a fallback walk ends still blind, or no walkable point lies within 2 m of the aim: reported as the current `OutOfRange` or `NoLineOfSight`); or the walk makes no progress for 3 s. Progress is the flat distance to where the current walk leads falling by 0.05 m, the cover walk's rule (`AbilityStallTimeout` = `CoverWalkTimeout`, `CoverProgressStep`; no new numbers); a new walk starts from its current distance, so a series of fresh walks that go nowhere still gives up. A new order (Replace), Stop or a held move key replaces or cancels it like any other order.
  - **Not while steering (ruling R10).** While the unit has a non-zero move intent (the player is steering it), an ability whose only problem is range or sight is refused at once with that reason, as before 029: it would only be dropped by the steering on the next frame. `CommandableUnit.CanWalkToCast` is the one test; `Issue` passes it to `UnitAbilities.CanOrderNow(command, canWalk)` and `AbilityTargeting` passes it to the preview (`AbilityPreview.CanWalk`), so such an aim previews red with its reason and the ability stays armed. A usable ability issued while steering is accepted and runs on the next frame as in 025. A move intent set after the walk has started still cancels it.
  - **Queue and time.** A Shift-queued ability approaches the same way when its turn comes; queue-time validation stays static (who and what). The walk and the cast run on scaled time, so nothing moves while paused; the order is accepted and visible while paused for planning.
  - **Preview and debug.** `AbilityPreview.WillApproach` (armed, aimed, failing only on range or sight) sits between usable (`IsValid`) and refused. `AbilityTargetingView` draws the aim amber for it (green usable, red refused); `AbilityDescriptions.Preview` ends with "moving into range" or "moving to a firing position" instead of the failure, and the bar's running-order line says the same while the unit walks (`AbilityDescriptions.Running`). `CommandQueueView` already draws a line from the unit to the ability's aim, which is the walking direction; no change. Mouse clicks and the pad cursor's Confirm both reach `Issue` through `AbilityTargeting.Confirm`; no input change. Enemy AI and companions still do not use abilities.
  - **Tests:** pure rules and wording in `AbilityRulesTests` and `AbilityDescriptionsTests`; the behaviour in the new `CommandableUnitAbilityApproachPlayModeTests` (Aimed Shot out of range, behind a wall, Blast out of range and out of sight, Mend out of range, the refusals at once, the three ways to give up, pause, direct control and a new order); the mouse and pad paths in `AbilityTargetingTests` and `AbilityTargetingPadTests`; the views in `AbilityViewsTests`; the arena in `PrototypeSceneAbilityTests`. Tests that asserted the old refusal were rewritten to the new rule. Measured totals: EditMode 577 and PlayMode 581 tests, all green (baselines 571 and 568); after the steering rule (R10) and its tests, EditMode 577 and PlayMode 585.
- **Why:** the owner wants an ability order to behave like a click on an enemy; walking into range is what a player expects, and with the existing approach and reposition steps it costs one branch instead of a second movement system. The order itself carrying the phases keeps queueing, pause, direct control, Stop and companion parking working without any new code paths.
- **Rejected:** projecting the caster's future position for queue-time checks (still rejected: queue-time stays static, it needs path prediction); walking while the ability is on cooldown (refused at once with `OnCooldown`; a unit should not wander off for something it cannot use); a separate "ability approach" order type queued in front of the ability (two orders to keep in step for one intent, and Stop, Replace and parking would see the walk as a separate order); duplicating the attack's approach code for abilities (shared through `Aim` instead, so a fix to the chase or the firing-position search lands once); finishing a walk to a validated firing position before casting, as an attack does (a one-shot ability gains nothing from the extra steps).
- **Implications:** while steering, an out-of-range or blind ability order is refused, not walked to (ruling R10). An ability order may now last seconds; anything that reads `CurrentCommand is AbilityCommand` as "about to fire this frame" must use `AbilityPhase` instead. A future ability with a minimum range, a cone or a wind-up plugs into `UnitAbilities.CanUseFrom` and the `Check` order. Enemy AI could issue ability orders and get the approach for free.

The firing-position search is the attack's (16 candidates within 4 m of the unit, nearest first, no cover value), so a Blast or Aimed Shot may be cast from an exposed spot. The cast happens the first frame the line clears, so the unit can stop on a corner's edge (fine for a one-shot ability, unlike an attack). The give-up reason for an unreachable aim is the last `OutOfRange`/`NoLineOfSight`, not a separate "unreachable" value. A walk toward a ground point that has no walkable floor within 2 m logs `UnitMover`'s usual warning before it gives up, as an attack on such a target does.

The within-object proximity merge and its setting `mergeDistance` (0.9 m) are deleted; only an exact-duplicate guard remains (`CoverGenerator.DuplicateDistance`, 0.1 m: of two candidates of one object that close, the first is kept). A low wall never lies flush along a wall, a crate is never flush, and a 1-tile gap is never used (`MissionConstants.LowWallClearance` is removed). The first 20 of the 40 tries keep the 2-tile gap everywhere; the other 20 also allow the end-on position (`ObstaclePlacer.TryPlaceRandom(..., flushX, flushY)` draws only allowed start coordinates). Tall obstacles (2 tiles to walls), the 2-tile gap between obstacles, the door rule (nothing within 2 tiles of a corridor strip), connectivity, determinism and the bounded tries are unchanged; without a flush flag the draws are exactly the old ones, so only layouts that used the relaxed tries changed (golden hashes re-pinned). ## 031 — End caps only where a unit can go round the end

- **Decided (2026-10-06, amends 030 and 026):** owner, after screenshots of generated missions: at several wall ends next to an opening (a hallway mouth or a door gap) there were two cover markers close together: "the squares I highlighted red should only have 1 cover point at the very corner of the wall because they serve the same function", then "I think option A [the point beside the wall, a little back from the end, with the peek arrow] but you have to make it where the cover is an option as if coming from either direction, i.e. from inside the room or from the hallway."

## 032 — Wall runs are maximal and overlap at junctions

- **Decided (2026-10-06, amends 026):** owner, from a screenshot of a wall end at a hallway mouth: "Some of the corner cover points seem to be off a bit. They should be equal distance from the wall corner on both sides." The two corner points flanking the visible corner stood at different distances from it.
  - **Cause (measured).** Room-frame walls were cut into disjoint boxes by the greedy floor cover (`RectCover.Decompose`), so at an L junction (a corridor side wall meeting a room wall at a jamb) one box owned the junction tile and the other box stopped one wall thickness short of the visible corner. A corner point stands `cornerInset` (0.35 m) back from the end of its own box, so the point on the shorter box stood 1.35 m from the visible corner. Built missions, seeds 1 to 20, every corner location of a `Wall_n` measured along its peek direction to the nearest visible outer corner of the wall mass (a tile-grid point with exactly one wall tile among its four tiles): 764 locations, exactly half at 0.35 m and half at 1.35 m. Every one of the 381 non-flush jambs had one point at 0.35 m and the other at 1.35 m (room side long in 192, hallway side long in 189, depending on which box the row-by-row scan reached first).
  - **Fix (`MissionGenerator.AddWalls`, `RectCover.MaximalRuns`).** Wall boxes are now the maximal straight runs of wall tiles of length 2 or more, horizontal and vertical, overlapping at junction tiles (a junction tile is covered by exactly one horizontal and one vertical run); a wall tile in no run would be a 1 x 1 box (none occur with the default settings). Every straight wall face is therefore the face of one box that ends at the visible corner. Names stay `Wall_<n>`, numbered horizontal runs first (rows from y = 0), then vertical runs (by start tile), then single tiles. The wall mask stays one tile thick (no 2 x 2 block of wall tiles in seeds 1 to 200; a test asserts it over seeds 1 to 60); a thicker block would still be covered exactly, by stacked parallel runs. The floor keeps the greedy disjoint cover. Cover rules (027, 030, 031) and offsets (`standOffset` 0.75, `cornerInset` 0.35, `peekDistance` 1.25) are unchanged.
  - **Measured after.** Seeds 1 to 20: all 764 `Wall_n` corner locations stand 0.35 m from a visible corner (min = median = max = 0.35, no exceptions); all 381 non-flush jambs have both points at 0.35 m (difference 0.00). Seeds 1 to 40: 766 of 766 true jambs have a room-side and a hallway-side corner (142 flush jamb ends; this enumeration, the same as `MissionBuilderPlayModeTests`, counts 908 jamb ends where 031 recorded 928), no column on a `Wall_n`, every baffle keeps two end caps and every pillar four columns. Cover per mission (Low / Tall corners / columns) is unchanged for seeds 1 to 8 and 12345 (1: 11/56/20, 2: 8/56/16, 3: 28/58/16, 4: 28/64/20, 5: 35/60/28, 6: 12/68/20, 7: 19/66/16, 8: 19/56/16, 12345: 8/56/20), and so is the wall box count per mission (mean 39.7 over seeds 1 to 200: every old box became one run, with one junction tile per box). Walls do not feed any random draw, so every layout is the same apart from its wall boxes: attempt 1 succeeds for 152 of 200 (76%), mean 1.34 attempts, at most 5, low objects median 3; the 200 seeds generate in about 0.15 s (0.12 s before, within run-to-run noise). The arena (`Prototype`) is hand-built and unchanged (52 locations).
  - **Tests.** `MissionBuilderPlayModeTests.EveryOpeningJamb_HasItsTwoCornerPoints_EquallyFarFromTheVisibleCorner` (seeds 1 to 6 and 12345: both points of every non-flush jamb at 0.35 +- 0.05 m, and every `Wall_n` corner 0.35 m from a visible corner; it failed on the old decomposition with 1.35 m); the jamb enumeration of the 031 test moved into a shared helper. `MissionLayoutInvariantTests`: walls are one tile thick and the wall boxes are exactly the maximal runs plus single tiles (failed before). `MissionGeneratorTests`: `RectCover.MaximalRuns` on a hand mask (T, L, isolated tile, order); the wall test now says the union of the wall boxes is exactly the wall mask and that boxes overlap only at junction tiles (one horizontal and one vertical run), instead of "wall boxes do not overlap". The golden layout hashes (seeds 12345, 1 and 2) were re-pinned because the wall box set changed. Measured totals: EditMode 595 and PlayMode 588 tests, all green (baselines 593 and 587).
- **Why:** the owner's rule is about the visible corner, so each straight face must belong to a box that reaches it; maximal runs do that with a few lines in the layout and no change to the cover generator, which keeps treating boxes independently.
- **Rejected:** merging coplanar faces of neighbouring boxes in the cover generator (more general, also for hand-built scenes, but much more code; kept as the alternative if overlapping boxes ever cause visual or physics problems); moving the inset per face to compensate for the neighbouring box (the generator would need to know about other boxes anyway); accepting the asymmetry.
- **Implications:** wall boxes overlap at junction tiles (identical height and material); nothing downstream assumed disjoint boxes: the builder makes one cube per box, the NavMesh marks each box Not Walkable (a union), cover discovery treats boxes separately and drops candidates whose stand point falls inside the other box (not walkable), and the layout hash simply lists the boxes. The layout hash and the golden hashes changed; seeds, attempts and cover counts did not. A corner point's protecting collider is now the box that runs all the way to the corner.
- **Known limitations:** the overlapping boxes have coplanar faces at every junction tile (the end face of one run and the side face of the other, and the tops). With the current single untextured placeholder material both faces shade identically, so any depth tie is invisible, but this was not checked on screen; a textured or per-box material later could flicker there, and generator-side face merging (or trimming one run) is then the fix.

## 033 — Mission objectives, interaction and extraction

- **Decided (Phase 9, 2026-10-06):**
  - **Lifecycle:** `MissionState` (`Idle`, `Generating`, `Ready`, `Failed`) is unchanged and describes generation only; the new `MissionPhase` (`Inactive`, `Active`, `ExtractionOpen`, `Success`, `Failure`) describes play. A mission is `Active` the moment generation reaches `Ready` (no briefing). "Objectives complete" and "extraction available" are one phase because the extraction zone opens in the same tick the last required objective completes, so a separate state would never be observable. `Success` and `Failure` are terminal (later deaths, kills and zone entries change nothing, every interactable is disabled), and failure is judged before success in the same tick, so a dead squad never counts as extracted.
  - **Objectives:** `MissionObjective` is a plain C# class (`Id`, `Type`, `Title`, `State` of `Inactive`/`Active`/`Completed`/`Failed`, `IsRequired`, `IsKnown`, `HasTarget`/`TargetPosition`, `Describe()`, `Activate()`, pull-based `Evaluate()` called by `MissionRuntime.Tick()` from the director, so an active objective is re-derived from the world each frame and cannot drift from the scene). Three types: `EliminateHostilesObjective` (tied to its own list of `Health`, not to `Encounter`, so a mission may contain hostiles outside the group), `InteractObjective` (owns a `MissionInteractable`; completes on its `Completed` event) and `ReachZoneObjective` (centre, radius, required unit count; completes only while Active). Extraction is a non-required `ReachZoneObjective` that starts `Inactive` and is opened by the runtime. `IsKnown` separates existence from visibility (default true, nothing sets it false yet); prerequisite, optional, hidden, discovered and alternate objectives later fit as flags and an `Inactive` start without a rewrite.
  - **Victory:** `Encounter.Outcome` (and the `Prototype` scene's kill-all banner) is unchanged. No generated-mission behaviour reads `Victory`; the banner in a generated mission comes from `MissionPhase`, and `PrototypeHud` skips its own banner when a `MissionDirector` is wired.
  - **Placement:** `ObjectivePlacer.TryPlace` is a pure function of the layout, the settings and `SeededRandom.ForObjectives` (a salted second stream, so `ForAttempt` and the golden layout hashes are untouched). Terminal room: not the friendly room, graph distance at least half the maximum from it, preferring rooms with obstacles, tried in seeded shuffled order. Terminal tile: a tile whose 3x3 block is floor and free of boxes, inset from the room edge by the free radius (so never in a doorway), at least `SpawnSpacing` (2.5 m) from every spawn. Guards: up to `guardCount` (default 2) extra hostile tiles in the terminal room, 2 to 6 tiles from the terminal, more than 1 tile from every box, spaced from every spawn and `minTeamSeparation` from the friendlies; fewer than requested is allowed. Extraction: a room other than the terminal and friendly rooms when one exists, preferably 1 to 2 rooms from the terminal room, a free 3x3 tile at least `ExtractionClearance` (4 m) from every spawn and guard. The result is an `ObjectivePlan` with its own FNV-1a hash, pinned for seeds 12345 (18368419039347052969), 1 (1731673444590866448) and 2 (705921155356568738) in `ObjectivePlacerTests`. A placement failure fails the attempt like any other generation failure.
  - **Deviation from the owner's pipeline order:** placement and the terminal run before the build, not after it, because the terminal is solid and must be in the NavMesh bake; otherwise a runtime NavMesh carve or a second bake would be needed. `MissionBuilder.Build` takes a pre-bake content callback (so it stays ignorant of objectives), and after the bake `MissionNavigation.ValidateObjectives` checks a path from the first friendly spawn to the terminal, the extraction zone and every guard, and a standing place on the NavMesh within `InteractionRange - 0.2` of the terminal. A failed check fails the attempt.
  - **Ruling on the free-block size (plan defect):** the spec and plan asked for a 5x5 obstacle-free block (`FreeRadius = 2`, two free tiles on every side) around the terminal and the extraction tile. Measured over seeds 1 to 100: only 9.2% of generated layouts (131 of 1424) had any room with such a block, and placement succeeded for 0.4% (6 of 1424), because the generator keeps 2 tiles of obstacle clearance in 7 to 10 tile rooms. Ruling: `FreeRadius = 1` (a 3x3 free block) for both, terminal candidates limited to the room interior inset by that radius, and the post-bake NavMesh checks are the real guard on connectivity. The cost if this is wrong: terminals sit closer to obstacles and a pocket beside a terminal is possible (such a seed fails the post-bake checks and retries).
  - **Measured placement:** `attempt 1: 152/200, mean 1.34, max 5` over seeds 1 to 200 (`ObjectivePlacerTests`, with the inset rule), so 48 of 200 seeds needed more than one attempt. These numbers are identical to the layout-only figures of records 031 and 032 (76% at attempt 1): placement added no failed attempt over seeds 1 to 200, so the whole pipeline's attempt statistics are those of layout generation. Built end to end over seeds 1 to 40: 0 failed an attempt for an `objectives:` reason, 5 had other failed attempts (layout generation), mean 1.175 attempts, 0 failed generations.
  - **Guards and hostile counts:** a generated mission has `layout.HostileSpawns` plus up to `guardCount` guards; the guards are part of the group the eliminate objective tracks. Tests that counted hostiles were minimally updated (`MissionDirectorPlayModeTests`, `ProceduralMissionSceneTests`).
  - **Interaction:** `InteractCommand` is plain data (a new `UnitCommand`). `MissionInteractable` (MonoBehaviour on the terminal) owns the claim, progress and availability (range 1.8 m, duration 2 s from `interactionSeconds`, one user at a time). `UnitInteractor` (added to friendlies at spawn) owns the rules and failure reasons. The order's life is in `CommandableUnit`: validate on `Issue` (alive, has an interactor, target available, terminal position reachable; queued orders get the static checks only), walk to `terminal.Position` (there is no `StandPoint`: the terminal is solid, so it is a hole in the NavMesh and the mover snaps the destination to the nearest NavMesh point), stop in range, face the terminal, claim and advance progress, re-validate every frame, and on any failure, cancel (Stop, a replacing order, steering, death) or completion release the claim, so the queue moves on and a unit never sticks. Only a cancelled or failed order loses its progress; completion keeps the terminal completed. Progress advances with scaled time, so tactical pause freezes it and resume continues. The same `Issue` path serves direct control, paused tactical planning, queues and group orders; input code never touches objective state.
  - **Input:** a new semantic action `Commands/Interact` (keyboard R, no pad binding). A click or cursor Confirm on a terminal goes through `PlayerCommandInput.Act`; `PointerTargetKind.Interactable` and `CommandResolver` (attack, then interact, then cover, then move) carry it. The cursor snaps to the nearest available terminal within 1.5 m, after friendlies and hostiles and before cover. Controller (owner decision during brainstorming): Interact is context Confirm only, meaning that with the cursor hidden and an available terminal within 3 m of an ordered unit (the selection when paused or anything is selected, else the active character) that no other living unit is working, Confirm interacts, otherwise it attacks as before; no new pad button. The keyboard action, the context Confirm and the HUD prompt share one rule (`TryFindReachableTerminal`; the prompt for a controller with the cursor shown names only a terminal under the cursor, since Confirm then acts on what the cursor is on).
  - **Extraction and failure rule:** at least `extractionUnits` (default 1) living squad members inside the active zone (radius 2 m) complete the mission; units outside are ignored and nothing happens to abandoned units. Failure is the whole squad dead, or a required objective in the `Failed` state; the runtime's failure check is the extension point for later conditions.
  - **Regeneration:** every teardown detaches and drops the old runtime first (it unsubscribes, so nothing can fire into it), `ResetSystems` empties the `InteractableRegistry`, and the terminal, zone, markers and units all live under `GeneratedMissionRoot`, so destroying the root removes them. Pinned by `MissionRuntimePlayModeTests` (old runtime never changes again, new one differs), `MissionContentPlayModeTests` and `MissionObjectivesSceneTests` (registry holds exactly the new terminal, one zone, no old unit or marker survives repeated F6/F7, including mid-fight).
  - **Debug presentation:** `MissionHud` (IMGUI; a `MISSION` panel with `[x]`, `[ ]`, `[LOCKED]`, `[FAILED]`, SUCCESS/FAILURE banner, the interact prompt from the bindings, labels at known markers) and `ObjectiveMarker` (colour by state via a property block). It reads only `director.Runtime`.
  - **Measured totals:** EditMode 670 and PlayMode 659 tests, all green (baselines 595 and 588; PlayMode was 651 before the final-review fixes added 8).
- **Why:** the brief makes a mission an explicit flow (objectives, extraction, success, failure) and requires it to be reusable and independent of UI and input. A plain C# runtime with pull-based evaluation is testable in EditMode with fake world state, cannot drift from the scene, and keeps the player-facing parts (HUD, markers) as readers of one object. Putting the terminal in the bake avoids a runtime carve or rebake, and the post-bake path checks keep the guarantee that a generated mission is completable. Interacting through `CommandableUnit.Issue` gives tactical, queued and group use for free and keeps rules out of input callbacks. Context Confirm needs no new pad button and matches how a pad player already uses Confirm next to a target.
- **Rejected:** MonoBehaviour objectives (scene objects for pure state, harder to test); ScriptableObject objective definitions (runtime state would not live in them and there is no authoring need yet); placement after the bake with a runtime carve or rebake (more machinery, and the carve changes paths the validation already checked); objectives inside `MissionGenerator` or the layout hash (would change every golden layout hash and mix play content into layout generation); relaxing the generator or carving a 5x5 block to honour `FreeRadius = 2` (both change layout generation and golden layout hashes); keeping partial interaction progress (extra state for a 2 s action); a dedicated pad Interact button, R3 or the select/view button (owner chose context Confirm, and those buttons are already taken or poorly placed); a tick glyph in the IMGUI panel (the font may lack it, so plain `[x]`).
- **Implications:** a new objective type is a `MissionObjective` subclass plus a line in `MissionContent.CreateRuntime`; a new interactable is a `MissionInteractable` plus an objective; a mission feature that is solid geometry adds its content in the pre-bake callback. Placement stays room-grid specific (it reads `Layout.Rooms`, `Connections` and `Boxes`) and the plan is not part of `MissionLayout` or its hash. Generation can now also fail an attempt for placement or post-bake validation reasons. Changing placement rules changes the plan hashes (re-pin once, deliberately); the layout goldens are independent. Hidden or discovered objectives need only `IsKnown` and an `Inactive` start plus a view that honours them.
- **Known limitations:**
  - **Terminal ray targeting.** A terminal hit directly by the cursor ray is returned before friendly and hostile snapping and before `SnapTo` narrowing, so aiming a unit ability with the cursor on the terminal while a unit is within 1.2 m yields `NoTarget`.
  - **Terminal can be hidden by a tall obstacle.** From the default camera framing the terminal can stand behind a tall obstacle (seed 12345's terminal is behind a 3 m pillar), so it may not be clickable or cursor-targetable there while R and pad Confirm still work. This is the wall-occlusion limitation already open in 026, which the owner dropped for now.
  - **Silent give-ups.** An out-of-range give-up of an Interact order records no failure reason.
  - **Enemies are not objective-aware.** They do not react to a unit working at the terminal, and the guards have no guarding behaviour beyond their spawn place. The unit holding an Interact order does not shoot back: `AutoRetaliate` only acts on an idle unit, and `EnemyAI` and `CompanionAI` treat an Interact order as an explicit order.
  - **Working under fire.** A unit keeps working while it is being shot: damage does not interrupt the interaction (a design question for the owner).
  - **Play continues after the end.** After Success or Failure the units stay controllable and hostiles keep fighting; only the banner and the objective states change.
  - **`hackTerminal` off.** A terminal tile and the guards are still placed (guards stand around a terminal that does not exist), and a layout with no terminal tile still fails the attempt.
  - **Extraction beside hostiles.** The extraction room may be a hostile spawn room: harmless while `eliminateHostiles` is on, but with it off the zone can sit beside living hostiles.
  - **Ordered units decide what is in reach.** The pad's context Confirm and the keyboard Interact use the ordered units (the selection when paused, so paused R with nothing selected does nothing), and the HUD prompt follows the same rule (hidden then). The owner may later want paused R to fall back to the active character.
  - **Placement block size.** Placement could prefer a free 5x5 block when one exists and fall back to 3x3 (a possible later improvement; the plan hashes would be re-pinned).
  - **HUD placement unseen.** The `MissionHud` panel position (left, y 190, banner y 255) was not seen on screen and may overlap the prototype HUD.
  - **Interaction model.** Progress is lost on cancel and one unit works a terminal at a time; objective visibility is data only (`IsKnown`), nothing reveals or hides yet.
  - **Debug views.** `MissionDebugView` and the gizmo views do not show guards.
  - **Geometry.** The terminal is solid but not a `CoverSurface`, so it offers no cover.

  - Normal maps are assigned but there are no metallic, smoothness or emission maps (the glow strips are painted into the base colour); the body and rifle materials use a shared default smoothness of 0.5.

## 035 — Environment visual layer: planner, theme and builder

- **Decided (2026-10-07):**
  - **Structure:** the visual layer is a planner (`EnvironmentVisualPlanner`: pure, turns the layout into `VisualPlacement`s of semantic `EnvironmentElement`s), a theme (`EnvironmentTheme` ScriptableObject: element to prefab variants plus a `salt`) and a builder (`EnvironmentVisualBuilder`: instantiates the placements under one `Visuals` node). The generator never names a prefab.
  - **Gameplay unchanged:** the gameplay cubes stay the only carriers of the collider, `CoverSurface` and `NavMeshModifier`; when a theme is assigned their renderers are disabled. Prefabs are collider-free (the builder strips any it finds), so cover, navigation and the layout hash are identical with or without a theme.
  - **Walls:** per-tile modules (straight, end, corner, junction) classified from the neighbouring wall tiles; `Pillar`, `LowCover` and `LowCoverLong` (2-tile modules plus a remainder) cover the other obstacles; `DoorFrame` overlays the wall ends that ring an opening.
  - **Variants:** chosen by a stateless hash of seed, theme salt, element and tile (`VisualVariants.Pick`), not from a random stream.
  - **Terminal:** split into the gameplay root and a swappable `VisualRoot`; the objective marker tints only its display.
  - **Debug:** F8 toggles the gameplay cubes with their existing placeholder materials, for comparing art against the real volumes.
  - **Kit:** `EnvironmentKitBuilder` creates six `BW_` materials, primitive prefabs and the `CorporatePrototype` theme, keeping existing assets unless told to overwrite. Conventions are in `Docs/EnvironmentAssetGuide.md`.
- **Why:** art must be replaceable (and later themeable) without touching generation or gameplay, and the physical rules must not depend on what a wall looks like.
- **Rejected:** stretched single wall meshes (cannot carry trim or corners); colliders on visual prefabs (trim would create false cover and navigation faults); drawing variants from the layout random stream (any visual change would reshuffle the map); a decal or clutter framework (out of scope).
- **Implications:** replacing art needs no generator change; a new theme is a new asset; `DoorFrame` overlays ring wall ends; floors are per-tile modules, so instance count grows with mission size (static batching is the first optimisation if profiling asks; for runtime-instantiated visuals that means `StaticBatchingUtility.Combine` on the `Visuals` node, not editor static flags). `LightFixture` is an emissive prop only; real lights are not part of this phase. `ObjectiveMarker` now also tints `_EmissionColor` (tint x 1.5), so the terminal's emissive display shows its state.

## 036 — Persistent operatives: definition, state and mission unit

- **Decided:** An operative is three separate things. `OperativeDefinition` (ScriptableObject, immutable: authored GUID id, display name, role, unit prefab, base health and speed, archetype, starting abilities) says who they are. `PersistentOperativeState` (plain `[Serializable]` class: id, XP, picked choice ids) is what survives between missions; it lives in a scene-level `SquadRoster`. The mission unit (a spawned GameObject with `UnitIdentity`) is disposable and holds only runtime state (`Health` damage, cooldowns, orders). `EffectiveConfiguration.Evaluate(definition, state, track)` = definition + role bonus + the modifiers of the picked choices; `UnitIdentity` applies it to `Health`, `UnitMover`, `UnitAttacker` and `UnitAbilities`, at spawn and again whenever the roster reports a change. Rank and pending picks are derived from XP and the `ProgressionTrack` (never stored). XP: `ProgressionTrack.MissionCompletionXp` to every roster member when a mission ends in Success (dead operatives included), plus a debug key; no kill XP (Health.Died carries no killer). One pick per rank after the first, from four choices (combat, survivability, mobility, ability); picks stack.
- **Stable id:** a GUID string authored into the definition; the starting roster uses it, future recruits would get `Guid.NewGuid()`; the roster refuses blank and duplicate ids loudly. Never the display name (renameable), instance id, hierarchy or spawn order.
- **Health and death boundary:** runtime health exists only in `Health` and ends with the unit. Every mission spawns every operative at effective maximum health. A death changes nothing in the persistent state; the dead unit stays dead for its mission (existing behaviour). Injuries, recovery and permadeath are not built; the seam is the spawn step where effective maximum health is computed. `Health.SetMax` keeps damage already taken, so a live level-up raises current health by the difference.
- **Why:** a scene object must not be the identity of a character (models will change; missions are regenerated). Keeping the three layers apart means shared assets are never mutated (two operatives can share a role, archetype or ability asset), progression can be tested without a scene, and Phase 14 only has to serialize a list of `PersistentOperativeState`.
- **Rejected:** a generic modifier/stat framework (five named fields on `StatModifiers` do the job); storing rank or pending picks (could desynchronize); a static or DontDestroyOnLoad registry (global mutable state); progression on the unit component (the unit is destroyed with its mission); splitting the unit prefab into gameplay and visual prefabs now (it would rework Darius's animator wiring; `OperativeDefinition.unitPrefab` already makes the model replaceable without touching identity).
- **Implications:** persistence is in memory for the application session; reloading the scene resets the roster. `MissionSystems.roster` is optional: without it the legacy `FriendlySlot` path spawns the squad unchanged (to be removed once every scene uses a roster). Progression is never read by the mission generator and uses no random stream, so a seed produces the same mission whatever the squad has earned. Debug keys F9 (panel), F10 (+XP to the controlled operative) and F11 (reset its progression) are keyboard-only Developer actions. Phase 14 (save/load) should store `SquadRoster.States()` keyed by id and resolve definitions by id; a missing definition or choice id must degrade gracefully (choice ids already do).

## 037 — Mission intelligence: what exists versus what the player knows

- **Decided (2026-10-08):**
  - **Layers.** The mission (layout, NavMesh, colliders, objectives, AI) is never changed by knowledge. A knowledge layer sits between it and everything the player sees or can target: `MissionIntelligence` (pure model) is fed through a reveal API (`RevealRegion`, `RevealArea`, `ObserveEnemy`, `RevealDevice`, `RevealObjective`, `MarkLastKnown`) by `IntelligenceService`, and every consumer asks the service through an optional serialized reference and the `Knowledge` helpers. A null service or a fog-off mission means "everything known", so the default behaviour is Phase 10's.
  - **Knowledge-state model.** One enum, `KnowledgeState { Unknown, Discovered, Observed }`, for regions, devices and enemies. Regions and devices: Discovered is permanent, Observed is in sight this pass. Enemies: Discovered means last known (a marker), Observed means live. Only Observed enemies are targets.
  - **Region discovery.** Regions are the layout's rooms plus its corridor strips (`RegionMap`, derived from `MissionLayout`, not a second level representation). A friendly observes its own region and any region where a coarse sample point is within range (14 m) and in line of sight (the combat sight test): a closed wall reveals nothing behind it, an opening reveals what the aperture allows. Discovered layout persists; live sight does not. Passes run every 0.2 s of scaled time.
  - A region containing an observed hostile is observed too, so a seen unit is never drawn inside the dark (this reveals the room a shooter stands in).
  - **Last-known behaviour.** An enemy that leaves observation becomes a marker at the last seen position and is no longer tracked; it is not a target. The marker never clears by looking at its spot (see limitations).
  - **Exposure by firing.** A hostile that fires (hit or miss, `UnitAttacker.Attacked`/`Missed`) is Observed for `exposureSeconds` (3 s) wherever it is, then becomes last known. This keeps a long-range shooter from being both lethal and unanswerable.
  - **Objective knowledge.** Existence is separate from knowledge: `MissionObjective.IsKnown` (the decision 033 seam) is written only by the model. Starting knowledge is configured (`All`, `ExtractionAndTerminal`, `ExtractionOnly`, `None`); an objective with a place is learned when its region is observed (seen), so a known layout can keep objectives unknown; the elimination objective when the first hostile is observed. Unknown objectives are listed by a vague title ("Locate the data terminal") when the settings ask for it; the hostile count is replaced by kills. Completion logic never reads knowledge.
  - **Hacked cameras.** A camera-control terminal (a second `MissionInteractable`, available from the start, found like any device) compromises the camera network; hacked cameras observe by position, facing, range, a 90 degree field and line of sight, and stay live by default (`cameraStaysLive`; false gives a one-time reveal of what they cover). Devices (cameras, the terminal) are discovered by being seen. The camera terminal's device point is aimed 0.1 m above its box so sight can discover it (a point inside its own collider could never be seen). `SecurityPlacer` draws terminal and cameras from its own salted stream after the objectives.
  - **Recon Scan.** A ground-targeted ability with the new `Reveal` effect (range 18 m, radius 12 m, 25 s cooldown, 6 s, no line of sight needed), on Kestrel. It discovers every region the circle touches, discovers devices inside it and observes hostiles inside it for 6 s, through walls (a scan is not sight), then they become markers. It uses the existing ability, queue, pause and controller path unchanged.
  - **Anti-leak rules.** Targets: the pointer ray passes through unobserved hostile colliders and unknown terminals; cursor snap, cycling, soft target, Attack fallback, `AbilityTargeting.TargetHealth`, `UnitAbilities.Check` and companion assist all use the same test. Displays: unit labels, hostile counts, attack lines, order lines, cover markers (unknown regions, cover held by an unshown hostile), debug text and gizmos, objective counts. Ground abilities may be aimed anywhere in range, including undiscovered ground; their preview lists only observed hostiles while the effect still hits every hostile it should.
  - **Presentation.** `FogPresenter` darkens the floor plan with a feathered brightness grid (decision 038); `HostilePresenter` sets `Renderer.forceRenderingOff` on hidden hostiles and draws the last-known marker. Knowledge never lives in renderer flags.
  - **Debug.** F12 truth view (display only: targeting stays restricted), F5 next fog preset + regenerate the same seed, M map overlay; truth view shows region/enemy/objective/camera/scan data. The scene ships with the Blind preset; the code default is fog off.
- **Why:** the player's information must be a design variable (briefings, recon, cameras), not an accident of what is rendered. Keeping the model pure and the consumers behind one tiny query surface lets every system be gated without any of them learning how knowledge is gathered, and keeps generation, AI and combat untouched (same seed, same mission).
- **Rejected:** a tile-grid fog of war (costlier, not the unit the brief asks for, a second level representation); renderer-visibility flags as the data model (breaks with themes and cannot be queried); disabling or destroying unknown content (breaks NavMesh, AI and determinism); fogging enemy AI (the brief keeps its perception); each system keeping its own notion of "visible" (guarantees a leak); changing combat code for exposure (the existing attack events are enough).
- **Implications:** a new information source is one more caller of the reveal API; a new display of enemy or hidden-room data must go through `Knowledge`; Phase 12 may add clearing markers by sight, alerts, or fogged AI without touching the model's shape.
- **Known limitations:**
  - A unit already chasing a target keeps chasing after it leaves observation; its movement can hint at where the target is.
  - An ability order (Aimed Shot etc.) whose target leaves observation ends with the "no target" refusal, including one still walking into range or waiting in the queue; a plain Attack order keeps chasing (the first limitation). This is deliberate: it stops the unit walking toward a position the player no longer knows.
  - Last-known markers only update when the enemy is observed again; looking at an empty spot does not clear them.
  - A newly seen enemy appears up to 0.2 s late (pass interval).
  - Death marker discs are not hidden: a hostile that dies unseen leaves a disc.
  - The "discovered" veil depends on a runtime URP transparent material; without one a discovered region is simply clear.
  - A scan ignores walls, so it can mark an enemy behind several of them.
  - Companion assist acts only on observed hostiles; `AutoRetaliate` reacts to damage and is not gated.
  - A wall beside several regions takes the brightest of them, so it stays visible once any one of them is discovered.
  - The "Layout known" preset: the map is fully discovered, but placed objectives are learned only when their region is seen.
  - Unknown regions are drawn as dark rectangles on the overlay and as fog on the floor plan, so a `map = None` mission still shows where rooms and corridors are (the fog hides contents, not the room outlines).
  - Cover points held by an unshown hostile are omitted from the cover markers, but a click on one can still be refused by the cover rules, which hints at the occupancy.
  - Switching presets with F5 can change the layout of a same-seed mission when camera placement fails an attempt and a later attempt is used (Full has no cameras, Blind has three).
  - Fog presenters (`FogPresenter`, `DevicePresenter`) take their service reference at enable time: set the serialized fields before enabling, as the scene builder and the tests do.

## 038 — Fog of war as a feathered brightness grid

- **Decided (2026-10-09):**
  - **Brightness grid.** `FogField` (pure, no scene dependency) holds one brightness value per cell over the mission floor plan, 4 cells per metre: 0 hidden, 0.45 dim (discovered, not in sight), 1 clear (observed). `FogPresenter` paints it from the knowledge model (a region's state; a wall takes the brightest region beside it) whenever a region's state changes, never from renderer flags.
  - **Feathering that cannot leak.** Brightness rises by 1 per 1.5 m of distance from darker ground: each cell is the lowest of its own level and every other cell's level plus a slope times the distance to it. A cell is therefore never brighter than the knowledge allows; hidden ground stays exactly hidden and the whole ramp lies on the known side. The dark runs across walls like any ground, so a wall between a known and a hidden room fades into the black.
  - **Easing.** Displayed values move toward the target over 0.4 s (unscaled time, so it finishes while paused). A mission's own opening paints (everything in the frame `Begin` builds the fog) snap, so a mission starts with its first view clear instead of fading in.
  - **Drawing.** One collider-free box over the floor plan carries the `Blackglass/IntelFogOfWar` shader, drawn after everything else: per pixel it reads scene depth, rebuilds the world position, samples the grid at x and z and blends toward near-black by one minus brightness. The grid is uploaded as an R8 texture. `FogPresenter` requests the camera depth texture on `Camera.main`, so this works at every quality level; `Blackglass.asmdef` now references the URP runtime assembly.
- **Why:** the first version was one opaque cube per region and wall, which cannot have a soft edge: every boundary was a straight cut and hidden areas read as solid black blocks. A per-point brightness field gives a smooth fade into the dark that follows the geometry at any height.
- **Rejected:** retexturing the cubes (the edge stays a straight cut); a screen-space blur of the dark (leaks hidden ground into the lit side and shimmers with the camera); a renderer feature or post-process (a pipeline-level change to two render pipeline assets for one effect); blur that also brightens the hidden side (would show unknown ground); the earlier drifting-mist look (misread the request: the ask was a soft edge, not a cloud texture).
- **Implications:** anything that changes what a region shows goes through the knowledge state; the presenter repaints only when a region's state changes. The straight outline of a hidden room against empty background remains (it is the room's own silhouette), and the last-known marker is dimmed with the ground it sits on. Wall tops and faces are darkened by their own footprint, so a wall right beside a hidden room reads slightly dim from inside the known room.

## 039 — Blackglass Asset Studio: an external ingestion tool, with Unity doing all asset work

- **Decided (2026-10-08):**
  - **Two components.** `Tools/BlackglassAssetStudio` is a standalone WPF app (Core library, App, tests, `net10.0-windows`). It classifies files, builds a versioned JSON manifest (`schemaVersion` 1), stages copies of the sources and launches Unity in batch mode. `Assets/_Project/Editor/AssetPipeline` (asmdef `Blackglass.AssetPipeline.Editor`) reads the manifest and does every Unity operation with Unity's APIs, then writes a structured `result.json`. The app never writes `.meta`, `.prefab` or other serialized Unity files.
  - **One contract, compiled twice.** The manifest/result DTOs and three pure rules (`HeightScale`, `PathRules`, `AssetNaming`) are plain C# files in `.../AssetPipeline/Contract/`, compiled by Unity and linked into the .NET `Core` project. A golden JSON fixture is parsed by both test suites.
  - **Character height** is a visual scale only: Unity measures the posed mesh bounds, the scale is `target / measured` (manual override wins; unusable measurements are errors, never NaN), and it is applied to the `ImportedCharacter` child of a generated `<Name>_Visual.prefab`. Gameplay roots are never read or written; Darius_Player is untouched.
  - **Animation** is imported as Humanoid with Copy From Other Avatar (a shared Humanoid model, default Darius's) and one `clipAnimations` entry carrying loop and the three root bake-into-pose flags; no `.anim` copies (consistent with 034).
  - **Environment modules** use the existing `EnvironmentElement` names and the guide's footprint table; mismatches are warnings, never an automatic rescale; theme registration is an explicit append/replace through `SerializedObject`.
  - **Safety.** Assets the pipeline creates carry the `BlackglassStudio` label; only labelled assets are updated silently, any other existing asset needs an explicit `allowOverwrite`. Run files live in `%LocalAppData%` (last 10 kept), not in the project. Originals are never modified. Nothing is committed by the tool.
  - **GLB/glTF are refused in v0.1** (no built-in Unity importer; a package would bypass `ModelImporter`).
  - **Batch mode needs the Editor closed**; the app checks `Temp/UnityLockfile`. There is no Cancel while Unity runs.
- **Deviations from the design spec:** no `StartAssetEditing` bracket (each item is imported synchronously so it can be measured); Validate is local, and measured values come back from the import.
- **Why:** importing a model by hand repeats the same ModelImporter settings every time, and AI-generated meshes need a size correction that must not leak into gameplay colliders and ranges.
- **Rejected:** writing Unity YAML from the app (fragile, bypasses importer behaviour); scaling the gameplay root (changes colliders, agents, ranges, cover); a Unity-only editor window (the user wanted a standalone tool with drag and drop); glTFast now; a stored import database (labels in the `.meta` carry ownership).
- **Implications:** new profiles are one table row plus one importer; a schema change bumps `schemaVersion` on both sides; Blender automation, GLB, animation retargeting libraries and a read-only inspect mode are v0.2 candidates.
- **Known limitations:**
  - Source height is known only after an import.
  - Unity cannot skip meshes in animation FBXs.
  - Only a sibling `<name>.fbm` texture folder is copied (as `<target name>.fbm`, under the same ownership and overwrite rule); files removed from the source `.fbm` stay in the project on re-import.
  - Theme registration cannot remove variants.
  - FBX unit settings are left untouched, so a centimetre-declared file (the Darius FBX measures about 0.0188 m on a fresh import; its project `.meta` compensates with `globalScale` 100) gets an automatic visual correction of about x100 with a warning, and a model measuring under 0.01 m (`MinMeasuredHeight`) fails with an "unusable measurement" error until a manual scale is given. A unit-fix feature is a v0.2 candidate.
  - Unity 6000.3 exposes no `ModelImporter` animation import warnings, so Unity's own retargeting warnings are not forwarded into `result.json`; they are only in the Editor log (`unity.log` in the run folder).

## 042 — The tactical HUD: a snapshot boundary, no focus mode, a developer overlay

- **Decided (2026-10-09):**
  - **Boundary: gameplay, snapshot, view.** `HudSnapshotBuilder.Build(sources, snapshot, unscaledTime)` is the only code that reads gameplay for the HUD. It reads through `HudSources` (a serialized bag of optional references; a missing one hides the panel it feeds) into one reused `HudSnapshot`, in `LateUpdate` on unscaled time, so the HUD runs in tactical pause. Panels compare each value with what they last showed and write a `Text` or `Image` only on change (cached strings, a write counter the tests read). The HUD subscribes to no gameplay event and holds nothing per mission between frames except compare caches, so a regenerated mission cannot leave a stale reference. These caches are the last shown values, the prompt cache, the 10 Hz hover cache (`hovered`), the queue step cache (`stepCommands[]`, command references), the aiming-line cache (`armedTarget`), the `names` cache (object names by instance id), and each visible `SquadCardView.Card.Unit` (a hidden card drops it). Every one is compared by reference or re-guarded by `CanTarget` on the next `Build`, and none is read for display without that guard (see the `HudSnapshotBuilder` doc comment). Gameplay never references HUD code. The seams outside `Hud/` are `PointerBlocker`, `DeveloperOverlay`/`DeveloperOverlayInput`, `ActiveCharacter.TakeControl`/`SelectActiveIn`, and the press gate and `ResolveAt` in `PlayerCommandInput`.
  - **Squad.** The source is `MissionDirector.Friendlies` including dead units (they stay in the list until regeneration), else the selection roster; card order is the list order, which is the Tab order. A dead unit keeps its card as `DOWN` (dimmed, empty bar) and control passes as Tab does. State words: `CONTROL` (filled marker), `SELECTED` (outline marker) and, on companions only, one of `FOLLOWING` (attached, follow on), `ATTACHED` (attached, follow off), `PARKED`, `HOLDING`. `HOLDING` means "not following by design": the spawn hold (`CompanionAI.IsHeld`) or ordered cover occupancy. Meaning is carried by text and shape, not colour alone.
  - **Command queue.** The subject is the first selected unit while paused, else the controlled unit. Steps are listed with the current one prefixed `> ` and the others by number; real time shows up to 3, pause up to 8, then `+N`. An `Attack` step names its target only while `Knowledge.CanTarget` holds, otherwise it reads `Attack (target lost)`. `CLEAR` issues `StopCommand` through `GroupOrders.Issue` for the subject, the Stop action's order.
  - **Intelligence restrictions (extends 037).** Hostile name, health, position, cover and existence pass through `Knowledge.CanTarget` (observed only), or `IntelligenceService.StateOfEnemy` / `TryLastKnown` for a last-known mark; `Knowledge.IsShown` is never used, so the F12 truth view does not widen the HUD. There are no hostile or kill counters. An unknown objective appears only as its vague title and only when `ListsUnknownObjectives`; its real title, count and position are never read into the snapshot. Extraction reads `UNKNOWN` / `LOCKED` / `AVAILABLE` / `ACTIVE n/m IN ZONE` / `EXTRACTED`. A last-known mark takes its position only from `TryLastKnown`. Pooled and hidden labels are blanked, not just hidden, so no earlier text survives. A PlayMode sweep under the Blind preset asserts that no unobserved hostile's name, health or position appears in any HUD text or mark, across observe, lose and last-known, with the truth view on and off. With `HudSources.intelligence` unset the HUD fails open (everything known), as every other consumer does; a scene test pins that the shipped scenes wire it.
  - **Prompts.** `HudPrompts` chooses the list for the situation (real time, terminal in reach, paused, ability armed; at most six) and `PromptResolver.GetPrompt(action, family)` produces every word, so no key or button name is written in HUD code (a source scan test enforces it). The input family is polled each frame; the list is rebuilt when the family, the context or the controls asset changes. Nintendo Confirm and Cancel follow the bindings: Nintendo Cancel and Xbox Cancel both read "B" (the plan's expectation that they differ was wrong; the tests pin the resolver's text).
  - **Input without a focus mode.** The EventSystem uses `PointerOnlyInputModule` (an `InputSystemUIInputModule` whose move, submit and cancel actions are cleared on every enable); a scene's own module is stripped the same way. The HUD therefore never takes stick or button input. Every clickable element sends the request the existing input sends (`HudRequests`), and each has a controller equivalent that already exists: card click / Shift+click = `UnitSelection.Select` / `Toggle` (LB/RB; LT + Confirm adds), card double-click = `ActiveCharacter.TakeControl` (LB/RB), ability slot = `AbilityTargeting.Pick` (RT + D-pad), CLEAR = Stop (D-pad down), Follow chip = `ToggleFollow` (D-pad up), Pause chip = `TacticalPause.Toggle` (Start / Menu / Options / +). A test pins each row. `PointerBlocker` (no UI types) holds a test delegate that `HudPointerGate` installs over the visible blocking panels; `PlayerCommandInput` ignores a click or drag that began over one. The blocking rects, while visible, are the objectives panel, the top-right block, the squad cards, the operative panel, the shown prompt rows, and the pause and result banners (ruling R3: neither banner follows the hover, so blocking them cannot flicker). The Target panel and the world marks never block: the target panel follows the hover, which reads the gate, so blocking there would flicker and swallow the click on the hostile behind it. Camera right-drag and wheel zoom over the HUD are not gated.
  - **Player HUD versus developer overlay.** `DeveloperOverlay` (hidden by default) is toggled by `Developer/ToggleDebugOverlay` on F1, keyboard only like the other Developer actions. It gates four IMGUI views: `PrototypeHud` (everything except the drag-select box), `AbilityBarView`, `MissionHud` and `MissionDebugView`; each returns early when hidden, and a null overlay reference means visible, so old scenes and tests are unchanged. The drag-select box and the controller cursor are player-facing and never hidden. `OperativePanelView` (F9), `IntelligenceDebugView` (F12) and `IntelMapView` (M) keep their own toggles. World feedback views are not part of the overlay. The intel map is the one IMGUI view the HUD lays out: while the HUD is enabled it gives `IntelMapView` a placement (`HudSources.intelMap`, `IntelMapView.PanelSource`) that puts the map above the squad roster on the left, left-aligned with the cards and 12 canvas units above the top card, scaled with the canvas, following the roster as the squad changes size (on the roster's bottom margin with no cards); without the HUD the map keeps its bottom-right default. A very full objectives list can reach the map on short canvases (21:9).
  - **uGUI with legacy `Text`, built from code.** A screen-space overlay canvas (1920 x 1080 reference, match 0.5) is built once by `TacticalHud` through `HudFactory`, the single place text is created, so a later TextMeshPro switch is one class. `Blackglass.asmdef` references `UnityEngine.UI` (the ugui package's assembly name). `HudSceneBuilder` (`Blackglass/HUD/Wire Scenes`) adds the HUD, `PointerBlocker` and the overlay to `ProceduralMission` and `Prototype`, idempotently. It does not add an EventSystem: it only converts an existing EventSystem's module to `PointerOnlyInputModule`. When a scene has none, `TacticalHud.EnsureEventSystem` creates one at runtime, as a child of the `TacticalHud` object (a sibling of `HudCanvas`).
- **Why:** playtesting depended on IMGUI debug text that mixed player information with developer data and had no notion of what the player may know. One read-only pass over gameplay into plain data keeps every fog rule in one file where a sweep test can prove it, keeps views cheap, and keeps the HUD correct across regeneration without event bookkeeping. Having no focus mode leaves the pad controls exactly as designed and makes the HUD a mouse convenience over actions that already exist.
- **Rejected:** TextMeshPro (an essential-resources import and binary assets for a placeholder HUD); UI Toolkit (a second UI stack with its own picking and asynchronous layout in tests); event subscriptions for HUD updates (stale references after regeneration, ordering bugs); letting the tactical cursor click HUD elements, or a controller focus mode (changes `PointerTarget` and the input pipeline, new bindings in every pad family); gating clicks inside each gameplay component (the press-time gate is one place); reading `Knowledge.IsShown` (the truth view would leak into the player HUD); editing the IMGUI views beyond an early return.
- **Implications:** a new HUD element is a snapshot field, a builder line and a panel line; anything about an enemy or an unknown objective must go through the builder and its fog rules, and the sweep test must cover it. A new click target must either be registered in the gate or be information-only. Final art replaces `HudPortraits.Resolve` (returns `null` today) and the `HudFactory` text and image creation without touching the builder. The IMGUI debug views stay as the developer overlay until replaced one by one.
- **Known limitations:**
  - Portraits are a placeholder badge (initials and role letter); there are no icon glyphs, and prompts are plain label text.
  - No controller focus mode: a pad reaches HUD functions only through the existing actions, and the tactical cursor cannot click the HUD.
  - Cover status shows only what `UnitCover` reliably reports: Exposed, Low cover, Corner cover, Tall cover, Moving to cover.
  - The hostile under the mouse is resolved at 10 Hz (one raycast pass through `PlayerCommandInput.ResolveAt`), so the Target panel can lag the pointer by up to 0.1 s.
  - 4:3 screens: the squad column (460 x 472) and the operative panel (760 x 280) overlap by about 33 canvas units. 16:9, 16:10 and 21:9 are tested and clear.
  - `IntelligenceService.Clear()` without a regeneration fails open (inherited from 037); the director clears and empties the encounter in the same call, so gameplay never shows it.
  - The prompt cache does not notice a live rebind (there is no rebind UI); a family or context change rebuilds it.
  - The ability slot layout (the chip spans the top row; the text shrinks to a 10 px floor on the generic pad's longest chord) and the objective markers `[!]` Failed, `[-]` Locked, `[?]` Unknown need an eye check in the Editor.
  - Camera right-drag and wheel zoom over the HUD, and the ability-targeting preview following the pointer under the HUD, are not gated (cosmetic).
  - Some per-frame allocations remain in pre-existing functions the builder calls (objective `Describe()`, `MarkerLabel`, `ReachZone.Inside`, `PromptInteractable`, the 10 Hz `ResolveAt`); they are small.
  - Queue steps are numbered "2 " rather than "2. ".
  - Not implemented (optional follow-up): a warning when `HudSources.director` is set but `HudSources.intelligence` is not. That wiring would make the HUD fail open; today only the scene test pins the shipped scenes.
  - The card-click eligibility rule lives in `HudRequests.SelectUnit` (`ActiveCharacter.IsEligible`), so a click on a `DOWN` card is inert. The world click path (`PlayerCommandInput` on a unit) applies its own rules, so the two paths can differ for edge cases.
